# Engineering Decisions & Bug Log

A dated, reverse-chronological log of what was tried, what broke, and why the current defaults in `README.md` are what they are. `README.md` describes the system as it stands today; this file is the running "why," kept out of the README so reference and history don't keep drifting into one document. Newest entries first. Each entry names the commit(s) it came from.

## 2026-10-08 — The original query path and its three switches are deleted

**What went.** `query/retrieval.py` (`retrieve_chunks`, the two strategy classes, the identifier pin), `query/router.py` (`QueryRouter`), `query/legacy_trace.py`, `models.RetrievalTrace`, `UnplannedDecider`, `compare-retrieval`, and the settings `QUERY_ROUTER`, `QUERY_ENGINE` and `ANSWER_PARTIAL_COVERAGE`. `query_knowledge_base` (now `query/knowledge_base.py`) is a thin function over `QueryService`; the MCP's `search_knowledge_base` runs only the retrieval service.

**Why now.** The rewrite had done its job as a reference: the 22 characterization scenarios, the live snapshots under five settings, and the golden questions (10 questions x 2 runs, router off and on) were equal between the engines, and the one place where the new code deliberately differs (the pin, previous entry) was measured on its own. Keeping both would only keep the tangle.

**Consequences, said plainly.**
- The planner now runs for every question (one extra model call), and a corpus with no approved document type fails loudly at the first question instead of silently reading everything. (`QUERY_ROUTER` was off by default; the dev setups that never turned it on now need `load-catalog`.)
- **`ANSWER_PARTIAL_COVERAGE` was deleted with the strict refusal kept**, reversing the 2026-10-06 plan to make it the only behaviour. The user's reasoning, which the data supports: it only dresses up the real limit. With `RETRIEVAL_TOP_K=4` the answer model sees 2-4 of 18-24 candidate documents; partial coverage turned the refusal into an honest answer about whatever those chunks were, but did not raise the retrieval hit for the expected documents (q0036: answered, `independent_fact` right, `exact_match` retrieval and answer wrong). The earlier "6 of 7 fixed" was one run on questions chosen because they failed, graded leniently. The `independent_fact` columns of the synthesizer and precedent_seeker personas are therefore expected to fall; the real fix is a document-level reading flow for survey questions, which is a separate, open topic.
- The characterization scenarios keep their numbers under the new step names (`<step>.<list>`): the 18 scenarios without an identifier were checked against the original's recorded numbers (every mapped list and the final context equal) before the original was removed. The 4 scenarios with an identifier describe only the new behaviour; the random "ported function equals original" tests (300 inputs) went with the original, their rules are covered by unit tests of the steps (year quota, hubness reorder, taking turns across documents).
- `compare-retrieval` was deleted rather than ported: its decisions are recorded in this file, and with the pin gone "diversify" only shapes the year-reserved slots. `scripts/eval_cli.py` (the `make eval*` benchmark) was ported to build one retrieval service per variant from `dataclasses.replace(settings, ...)`.
- `retrieval-snapshot` now records `<step>.<list>` per step instead of the original trace keys, so old snapshot files are not comparable with new ones (the command refuses nothing by itself; take a new baseline).

**Measured on** (the day's last numbers): `routing-eval` through the real decider, 28 of 28 (14 cases x 2); the three `exact` cases give the same numbers as the original router; a real `retrieval-snapshot` run twice on two questions, identical. Not measured: the full 33 questions on the new path (kept for after the survey-question work, 2 questions per persona until then).

## 2026-10-08 — The identifier pin is deleted from the new pipeline; one of its jobs had to move, and measuring is what showed it

**What was removed.** `IdentifierPinStep`, the `PINS` slot, the cross-encoder score-gate protection of a pinned chunk, and the pin half of the guaranteed slots in the final cut (the original engine keeps all of it until it is deleted). The metadata resolver (three steps, 2026-10-07) finds the documents the question names, the scope restricts the store to them, so a text search over chunks to "rescue" the identifier is a second, weaker way to do the same.

**What the measurement showed.** The first version of the deletion regressed one golden question: q0018 (two case numbers in the question) went from a correct answer 2 of 2 to a refusal 2 of 2. Both documents were in the scope, but the four final chunks all came from one of them, so the model had nothing to say about the other and (correctly) refused. The pin had hidden this: it did not only *find* the documents, its final-cut rule *took turns across them*. That second job does not belong to a text search; it belongs to the scope, because only the scope knows that the question named several documents. So `Scope.names_several_documents` becomes `RetrievalContext.spread_documents`, and the top-k step takes turns across documents when it is set (one named document: nothing changes). With that, q0018 was 2 of 2 again.

**Measured on** the 10 golden questions that contain an identifier (q0001, 2, 3, 4, 5, 8, 9, 12, 16, 18), 2 runs each, `QUERY_ENGINE=v2`, `QUERY_ROUTER=true`, local database, live Vertex models: with the pin 8 of 10 questions answered correctly; without it and without the spread rule 7 (q0018 lost); without it and with the spread rule 8, q0012's `exact_match` answer 1 of 2 instead of 0 of 2 (two runs: this may be noise). q0016 ("33/A", the pin's known false positive, which pinned documents that only cite the number) stays unanswered either way, but its retrieval-hit column is now honestly 0 instead of a pinned wrong document. This is a small sample; the full 33-question run is still to do at the end.

**Why this is recorded.** "The resolver makes the pin unnecessary" was a claim; the pin's *side effects* were not on the list when it was made (the design doc listed the slot, the guaranteed slots and the diversify flag, but not what they were doing for a two-document question). Characterization scenarios that describe the pin (`one_identifier` and three more) now run on the original engine only; on the new one a test pins that an identifier no longer pulls chunks in.

## 2026-10-07 — The metadata resolver was weaker than the text pin it is to replace; measured, then made at least as good

**The claim that did not hold.** I had said the identifier pin could go once the resolver exists, and that a question that writes a case number in another style (the golden q0008, "P.20103.2022.19" for the stored "4.P.20.103/2022/19-ítélet") did not need the pin because the text search would not find it either. Both were wrong. A review (an independent Opus read of the work) asked for the measurement before deleting anything, and a DB-only run (no model) of the resolver against the pin on real documents showed: on the exact written form both find the document (12 of 12); on the **same number written with spaces** ("10. P. 20.277/2019/77") the resolver found **0 of 12** and the pin **12 of 12**; **without the leading court number** ("P.20.277/2019/77") 0 of 12 against 12 of 12; with a Hungarian ending ("…/4-es") neither found it. On the 10 golden questions that name an identifier the resolver found the cited document in 6, the pin in 8. The pin's letter-and-digit comparison is more tolerant than a normalised prefix rule, and the question-side tokenizer cuts a spaced number at the space.

**Why it is not a normalisation problem.** The normalisation (case, spaces, a trailing full stop) works: the lower-case-with-a-full-stop variant was 12 of 12. What the pin does beyond it are two other relations: the wanted number is a **part** of the stored one (the leading series is left out, the spaced form loses its start in the tokenizer too), and the number is the stored one **with other separators**. They are different relationships, not formats, and each is a step of its own in the resolver, tried only when the earlier ones found nothing, reported by how it was found (`partial`, `compact`) so the scope and the explain record can say so.

**What was built, and the guards.** The two steps (`identifier_contains`, `identifier_compact_contains`, with the same rules as SQL regexes and an equality test between each Python rule and its SQL for awkward stored and wished values); a **strength floor** on what may match a part or without separators (at least six letters and digits, a digit, not a date, some structure) and on what may match as a *prefix* in the first step, because the review pointed out that a short token such as "4.P" resolved to every number that starts that way and then replaced the planner's filters; the Hungarian case ending taken off in the language layer (`query/inflection.py`), not in the generic rules and not in the original `store.py`. After: all five written variants resolve 12 of 12 (the pin 12 of 12 on the same tokens), q0008 resolves, and the golden count is 7 of 10 against the pin's 8; the remaining difference is q0016 (`33/A`, a statute paragraph the tokenizer takes for an identifier), where the pin hits 22 documents by accident and the resolver correctly finds none.

**Still open.** The pin is not deleted: the review's other points (the decider must keep the router's behaviour when a named identifier resolves to nothing, and unresolved identifiers belong in the scope's note; the scope must reach the retrieval; the golden eval cannot run on the new engine yet because it passes strategy objects) come first. A question that cites a case (q0018 now resolves the cited number to its own document too) widens the scope with the cited case; whether that is wanted needs routing cases.

## 2026-10-07 — The eval did not recognise two of the system's own refusals, found while separating the new code from the old

**What was found.** Putting the wording of every refusal in one place (`RefusalRenderer` in `query/outcome.py`, so the new pipeline does not have to import the original router for its sentences) came with a test that every sentence the system itself says must read as a decline to `query.decline_detection`, which the eval uses to tell an honest refusal from an answer. Two did not: "This kind of question is not supported yet ..." and "I could not interpret this question ...". Only "no documents match" had been added to the detector when that refusal was introduced; the other two came with the "not supported yet" outcome (2026-10-06) and were never added.

**Effect.** For an answerable question either refusal is a failure either way. For an *unanswerable* one (an adversarial question the router sends to "not supported yet") the eval would have counted the honest refusal as a hallucinated answer. It could not have lowered a measured number so far (no adversarial question took that path), but it was a trap for the first one that does. The detector now recognises both, with a test for each sentence and one that a sentence that merely contains "support" is not a decline.

**The separation itself.** The new pipeline's modules do not import `query/retrieval.py` or `query/router.py` any more, and a test (`tests/unit/query_pipeline/test_separation.py`) fails when one does, so deleting the original later is a deletion and not a rewrite. The wording (`NO_RESULTS_MESSAGE`, `NOT_SUPPORTED_MESSAGE`, `COULD_NOT_INTERPRET_MESSAGE`, the empty-filter sentence) and `as_routed` moved into the new modules; the original modules import them from there, and their names stay available in them, so no existing caller or test changed. A test holds the refusal renderer's text equal, word for word, to what the original router says for the same three refusals.

## 2026-10-07 — Identifiers get a value type of their own, and one rule for comparing them

**Why.** An identifier (a case number, an invoice number) is written in many forms: with spaces ("10. P. 20.277/2019/77."), with a trailing full stop, in capitals or not, with a suffix that names the copy ("-ítélet", "/II", "-III"). As plain `text` it was compared by an exact match plus a hand-written trailing-punctuation trim, so a question that wrote the number a little differently found nothing, and the step that made up for it was a full-text search over every chunk (5.5 s on one question in the funnel) that also pinned the *citing* documents when the cited one was absent. The aim is to resolve a question's identifier to its documents **from the metadata**, in one rule that every consumer shares, and for the general code to find the identifier keys by their type rather than by a corpus-specific key name.

**What was built.** A value type `identifier` (migration 0007 widens the `CHECK` on `meta_keys.value_type`; the values stay in `value_text`, so nothing is re-extracted). `metadata/identifiers.py` defines the rule: both sides are normalised (compatibility form, lower case, no whitespace, no `./-,;:` at either end), and a stored identifier matches a wanted one when they are equal or when it **continues the wanted one with something that is not a digit** (a suffix; not a digit, or `.../4` would match `.../40`). The plan compiler compiles `eq`, `in` and `contains` on an identifier key to SQL that repeats the rule on the stored value. The planner's prompt describes the type. `document_identifier` in the catalog is now of this type.

**Two risks, and what holds them.** The rule is written twice (Python and SQL), so a database test decides every pair of 16 awkward stored values and 15 wished ones (spaces, case, full stops, suffixes, a longer number, `_` and `%` that mean something to `LIKE`, full-width and no-break characters) with both and requires them to agree; the compiler tests pin the bound parameters and that the value is never part of the SQL. Retyping a key would have been read by the catalog loader as a changed definition and bumped its version, which makes every extracted value stale and means a full re-extraction (2224 documents) for a change that touches no value, so a change **between `text` and `identifier` alone** keeps the version (`retyped` in the import result; any other change at the same time is still a revision). Breaking each of these on purpose (the digit boundary, the trimming, NFKC, lower-casing, the `LIKE` escapes, the retype guard, the migration's `down`) fails a test; the full suite (unit + database, 1470) is green.

**Measured on the real data.** Retyped in the dev database: the key stays at version 3 and all 2224 values are still present. The planner measures did not move: `routing-eval` 28/28, the exact-answer planner eval 24/24 on two runs (one earlier run gave 23/24 on a rolling-date question, the planner's own variance: it did not repeat).

**Next.** The resolver that turns a question's identifier into a set of documents with this rule (and the scope that restricts the retrieval to them), then removing the identifier pin and its plumbing once the single-document questions are shown to hold without it.

## 2026-10-07 — A decision's second number was never stored: `document_identifier` came from the first 100 characters

**What was seen.** A golden question names a case as `8.P.XI.21.329/2024/12`, but the stored `document_identifier` of that document was only `8.P.21.329/2024/12-III`, so the number could not be resolved from the metadata. The document states both: the page header carries the decision's own number (`8.P.21.329/2024/12-III`), and further down the text says "Az ügy száma: 8.P.XI.21.329/2024/12." (the case number), and some decisions also say "Az ítélet száma:" (the decision number). They are two different identifiers.

**Why it was missed.** `document_identifier` was not extracted by the model at all: `scripts/meta_cli.py` copied it from the chunks' `document_identifiers`, which ingestion fills with a regex over the **first 100 characters** of the text. The "Az ügy száma:" line comes later. Changing the key's description therefore changed nothing (a first attempt did exactly that, and the 30 sampled values stayed the same), which was found only by asking why the description had no effect.

**Fix.** `document_identifier` is no longer a deterministic field: the model extracts it, quoting each value, from the same evidence chunks as the other keys, with a description that says to store every number the document states for itself (the case number, the decision's number, the header form) and not the number of another case that the text merely mentions. The key's version was bumped so every document is extracted again for this key only (the other keys are at their current version and are not asked again).

**Regex or model.** A larger deterministic head was measured first against the model's values on a 31-document sample, counting a written variant of the same number (`/ii`, `/ítélet`, a page number) as the same number, which is what the resolver will do: the current regex finds 47 of the model's 55 numbers with 3 values the model did not give; reading labels as well ("Az ügy száma:") finds 48 with 8 such values. Widening the head only adds numbers of *other* cases that the text mentions (a first-instance case in an appeal) and fragments, which would make an identifier resolve to the wrong document. The model tells a document's own number from a mentioned one, so it was chosen; the regex gain was one number for five noisy ones.

**Two wrong explanations on the way, worth recording.** I first said the second form was invented by the summary writer, then that it was one number written two ways. Both were wrong, and what settled it each time was reading the **whole text** of the document, not a snippet or its summary. The same goes for the file name, which is not an arbiter of the case number (a decision's number carries the sequence number, the case number can lack it): the text decides.

**Speed.** The extraction waits on the network (about 2 s per document, almost no CPU), so `extract-meta --workers N` runs the model calls of N documents at once. The database is only touched from the main thread (it reads a document's chunks, hands the API work to a worker, writes the result when it returns), only `2 * N` documents are in flight, and a worker count changes the speed and nothing else (tested: same values and report for 1, 2, 4 and 16; 8 deliberate breakages are all caught). Measured: 24 documents in 10 s with 8 workers (the calls add up to 72 s, a 7x speed-up). One call took 68 s in one run (the provider's latency tail), which is why two 40-document runs took 84 and 119 s; in a full run a stalled call holds one of the eight workers only. The access-token refresh got a lock, since several workers finding the token stale started one `gcloud` process each.

## 2026-10-06 — Two separate periods in one question made two filters that could never both hold

**What was seen.** While comparing the two retrieval engines on the real database, the golden question about "the 2021 and 2023 judgments" was answered "No documents match the filter (... decision_date between 2021... AND decision_date between 2023...)". The planner had written two `between` filters on the same date key; all filters must hold at once, so no document can match, and the router refused a question that could have been read. Found by looking at what the router *did* with a plan, not by any existing measure: `routing-eval` checks the flow the plan picks (here `lookup`, which was right) and the answer-level eval would have shown only a refusal.

**Fix.** A date key now accepts the operator `in` with a list of date specs, compiled as an OR of ranges in one filter (`metadata/compiler.py`); the planner prompt says that several separate periods of one key are one `in` filter, never two filters, and that a span ("from 2020 to 2022") is still one `between`. `routing-eval` now also executes the restriction of every lookup that is restricted and reports "lookup with an empty restriction" when it selects no document, so this class of plan can be seen. Measured on the question itself, 10 planner calls each: old prompt 1 empty restriction, 8 unrestricted, 1 fine; new prompt 10 of 10 put both years into one `in` filter and the restriction selected documents. The existing measures did not move: `routing-eval` 42/42 (old prompt 45/45 with the case that is described below), the exact-answer planner eval 24/24.

**What it did not settle, and a case that was removed.** I first added the question as a routing case expecting `lookup`. That was wrong, and the user said so: the question asks what kinds of disputes appear in two years' decisions, so reading the best four chunks cannot answer it, and the case encoded the wrong expectation. It was removed again. Where such a survey question should go (say "not supported yet", an `overview` over the matching documents' summaries, or the passages flow with the gap stated) is open: saying "not supported" would also catch the "how did the practice develop" questions that the filter restriction and the partial-coverage wording measurably helped (38 -> 47 of 78), so it is to be decided on a count of how many golden questions are surveys, not on this one.

## 2026-10-06 — The retrieval is rewritten as steps beside the old code, and proven equal before anything is switched

**Why.** `select_chunks` did ten things in one method, "no answer" was decided in four places with three different wordings, identifiers and years were detected in several places, and one cross-encoder class check silently decided whether a threshold applied. Patching that would only have rearranged it, so the path from `retrieve_chunks` to the chosen chunks was rewritten from zero as small classes, **beside** the old code, which stays the reference until the new one is proven equal. Design: `docs/query-pipeline-design.md` (as-is map: `docs/query-workflow.md`); commits `03e8334`, `e6d7739`, `a710672` and the wiring commit after them.

**Decisions made on the way (and why).** One frozen `RetrievalContext` with *named slots* (a slot is named for what it holds, not for the phase that wrote it; the old trace key `listwise` is exactly the kind of name that rots), a step returns a changed copy, so the observer sees before and after and a step cannot write what it did not declare. Steps declare `requires` / `provides` and the chain is refused when it is built if it cannot work. A refusal is a value (`Declined(reason, stage)`), not an empty list. The two retrieval gates were **not** merged (cosine before fusion, deliberately; the reranker's score after the rerank: different signals at different points), only their type and wording are shared. Profiles are registered data chosen by name (every free combination would be an unmeasured pipeline). Logging is an observer told after each step, **not** a decorator on each step, and retries stay in the drivers (a step-level retry would multiply attempts). `QUERY_ENGINE=legacy|v2` is a temporary switch for the comparison only. Deleting `QUERY_ROUTER` / `ANSWER_PARTIAL_COVERAGE` is *not* part of this rewrite: both default to off, so deleting them changes the default behaviour.

**How "equal" was shown.** Every characterization scenario (22) runs on the original engine, on the new pipeline and through `retrieve_chunks` with `QUERY_ENGINE=v2`, with the same pinned result. The two steps that were *ported* from private functions (the top-k cut with guarantees, CSLS) are also compared with those functions on 150 random inputs each, score ties included. Then `retrieval-snapshot` on six golden questions chosen to exercise every new step (a case number, a non-existent case number, a topic with years, a plain topic, one year, two years) was IDENTICAL between the engines under five settings: default, `RETRIEVAL_PERIOD_FILTER=true`, `RETRIEVAL_STRATEGY=vector`, `RERANKER_DRIVER=cross_encoder` (the score gate really dropped chunks: 40 -> 37 and 38 -> 29), and cross-encoder + period filter + non-diversified guarantees together. The old engine was first shown to be identical to itself. Not covered live: the listwise step (an LLM call, not deterministic; covered with a stub), and the full 33 questions (kept for the end).

**What the measurement of the tests themselves taught.** Breaking the code on purpose (mutation) found holes the green scenarios hid: five of the first fifteen breakages of the step code survived, because a fake store ignores the arguments a step passes (a search limit, `per_token`, `years` together with a metadata filter) and because some behaviours need a scenario that did not exist (the period filter on but no year in the question; a reranker that is not a cross-encoder, which has no score gate). They were closed with step-level tests that spy on the store and with three new scenarios; 38 deliberate breakages of the new code are now all caught. Two slips of my own are worth recording: a first mutation round that proved nothing because a macOS `sed -i` silently did not run (the "all green" meant "nothing was mutated"), and the cross-encoder live run failing for a reason unrelated to the rewrite (`.env` carries the Vertex ranker's model name in `RERANKER_MODEL`, so the cross-encoder must be run with its own model name too).

## 2026-10-06 — Step 1: the planner always decides, "not supported yet" is said plainly (and the regression it caused)

**The failure that started it.** Asked "list 5 cases similar to case X" (X named by its case number), the system returned a context made entirely of X (the identifier pulled in every chunk of its document and filled all four slots) and answered *"I could not find this information"*, even with the partial-coverage wording. The router skipped the planner whenever an identifier was in the question. The identifier is a **parameter** (which document the question is about), not an **intent**: the same case number can go with "who represents the defendant" (read that document) or "find cases like it" (not supported yet).

**What changed.** The planner always decides when the router is on; the "identifier -> skip the planner" shortcut is gone. There is a new plan operation `unsupported` with a required `reason` (in the question's language), used only for requests for documents *similar or related to a named one*; the router answers it plainly (*"This kind of question is not supported yet ... (reason)"*) instead of sending it to a search that cannot serve it. Ordinary content questions, comparisons of named cases and questions about the practice in general stay `lookup` (the passages flow); nothing was built for similarity itself. The rule "an exact plan with a residual is read, not counted" became one shared function, `as_routed`, used by the router and the routing eval. `corpus/cli.py routing-eval` (cases in `corpus/data/routing_cases.json`, planner only, cheap) measures the router's *decision*, which the golden-set eval cannot: it grades answers.

**The first version regressed the single-document questions, and the answers did not say why.** Seven golden questions (case-number lookups and the two adversarial ones) fell: fact_finder 100% -> 50%, practical_procedural 100% -> 75%, adversarial decline 100% -> 25%. Cause: now that they reached the planner, it put the `document_identifier` key into the **filters of the lookup** (`document_identifier = '4.P.20.409/2023/4.'`), and the router restricts a lookup to the documents the filters match, so a miss meant *"No documents match the filter"* and nothing was read. Two independent reasons the match missed: the value copied from the sentence carried the **sentence's trailing full stop**, and the stored identifier is a written variant (`4.P.20.409/2023/4-ítélet`); and a second, unrelated one: that document has **no stored court name** (anonymised), so `issuing_body = ...` could not match either. A metadata restriction can only exclude a named document.

**Fixes, in the order they were found:** (1) a prompt rule: never put an identifier in the filters of a lookup (cut the failures but a model follows a prompt rule only most of the time: 2 of 14 runs still did); (2) exact text matching ignores a trailing sentence full stop on both sides (`rtrim`), `contains` too (generic: a value copied out of a sentence often carries its full stop); (3) the structural fix: **a lookup that names an identifier is not restricted by the plan's filters at all**; the retrieval finds the named document itself (identifier pinning, normalised). The restriction is for broad questions (a court and a year, hundreds of documents). (4) the decline detector now recognises the router's own plain refusal (*"No documents match ..."*): for an invented case number that is a correct refusal.

**Measured after the fixes** (router on, partial coverage on): the seven single-document questions x3: adversarial **6/6** declined, fact_finder **9/9**, practical_procedural **6/6**; content personas (precedent_seeker, synthesizer, `independent_fact`) 4/4 and 4/4; the **retrieval snapshot is identical** to the baseline (retrieval was not touched); the routing eval (13 cases x3) **42/42**: every "similar" request (Hungarian and English, three wordings) is `unsupported`, every case-number question and every synthesis question is a lookup, every count/list is exact. The real "similar cases" question now answers *"This kind of question is not supported yet ... (A kérdés hasonló ügyek listázását kéri.)"*.

**Limits and what it shows.** The routing cases are 13 questions that I wrote, and one of them was wrong (a court that is not in the corpus; the planner was right); the identifier is detected by the same token extractor the retrieval uses (still two independent detections, see the design review); the not-supported detection needs `QUERY_ROUTER` on, with it off the old behaviour stays; the single-document set is only seven questions. The regression was found only because the single-document personas were re-run after the change: **a routing change must be measured on the cases it can break, not only on the ones it was meant to fix.**

## 2026-10-06 — Before restructuring retrieval: pin what it does today (and a nondeterminism that came out of it)

Retrieval is about to be restructured (steps pulled out of `HybridRetrievalStrategy`, a shared state, profiles per kind of question; see the design discussion). It is also the most heavily measured part of the system, so the first step is to be able to *prove* a refactor changed nothing.

- **Characterization tests** (`tests/unit/query_pipeline/test_retrieval_characterization.py`): a small deterministic corpus, a fake store that really filters by year/metadata/document set and really searches by identifier, a fake reranker; the whole of `retrieve_chunks` runs and, per scenario, the ids every recorded stage held and the final context are pinned. Fourteen scenarios: plain, years, one identifier, two identifiers with and without the diversified guarantee, identifier plus topic, the cross-encoder rejecting everything, the cosine gate failing, the listwise rerank, the vector strategy, a metadata filter, a restricted store, CSLS demoting a generic chunk, `top_k`. They say what the pipeline *does*, not that it is right. **Mutation-tested:** four deliberate breakages (skip CSLS, cap the identifier guarantee one short, drop the cross-encoder threshold, ignore the period reserve) all fail it; the first version did **not** catch "skip CSLS" because no fixture chunk had a hub score, so a CSLS scenario was added.
- **Things the pinning made visible** (none changed): the recorded stage named `listwise` is also written when listwise is *off*, then holding the list after the cross-encoder threshold; when the cross-encoder scores every chunk below the threshold the final list is empty although the cosine gate passed (a second, hidden "no result"); an identifier pulls every chunk of its document in as a guaranteed match and they fill the whole context, which is why "five similar cases to X" gets nothing but X.
- **A live snapshot** (`corpus/cli.py retrieval-snapshot --out F` / `--compare F`) records the same for the 33 golden questions on the real data and refuses to compare snapshots taken under different retrieval settings.
- **That snapshot found a real nondeterminism:** two identical runs differed in 6 of 33 questions (20 stage differences), all starting in the **full-text search**: `ORDER BY score DESC LIMIT 20` returns rows of equal `ts_rank` in an arbitrary order, and the cut can fall through a tie differently on each run. This also injects noise into every eval. Fixed with a tie-breaker (`ORDER BY score DESC, id`; the identifier search got `ORDER BY id` for the same reason). After the fix three runs were bit-identical. The tie-break test first passed even without the fix (six equal rows happened to sit in id order); it now uses forty rows whose physical order is shuffled by updates and fails without the tie-breaker. ## 2026-10-06 — The planner chooses the document type; a fused JSON object had silently dropped a filter

Step 5 of the document-type work: nothing about *which kind of document* is configured any more. The planner is shown every approved type with its description and its own keys and puts its choice in the plan (`"document_type"`, required, `null` only for a `lookup`); `QUERY_ROUTER_DOC_TYPE` is deleted. The compiler adds `document_type = ...` to the matching, so "how many invoices" counts only invoices; a document with **no type yet** counts as *unknown* (it may be of this type), not as a non-match. `extract-meta`, `coverage` and the stored-value lists are per type (a type's keys are never asked of another type's documents or of untyped ones), and the CLI's `--doc-type` default `court_decision`, a corpus-specific name inside generic tooling, is gone. A lookup that names only a type is restricted to that type's documents.

- **A count/list/sum/overview needs a type** (a plan that says `null` with one of them is rejected and retried): otherwise "how many invoices" in a corpus without that type could quietly become a count of *all* documents. A question that fits no known type is read, not counted.
- **A silent filter loss, found by measuring, not by tests.** The first measurement with the new prompt dropped from 24/24 to 79-92%. The cause was not the prompt's logic: the model had written two filters as *one* JSON object (no `}, {` between them), so `"key"`, `"op"` and `"value"` each appeared twice, and Python's parser silently keeps the **last** value: the court filter vanished and the count of "a court's documents last May" ran over the date alone and was presented as exact (56 instead of 4). This is the worst failure class for this feature (a confident wrong number). `extract_json(..., reject_duplicate_keys=True)` now raises on a repeated key; the planner, the metadata extractor and the type classifier use it (the grader keeps the tolerant mode), and the planner's one retry shows the model the exact complaint. The real fused reply is a regression test.
- **A second, separate miss was the prompt's own fault:** generic questions ("how many documents were dated next month") were planned as a null-type lookup even though only one type exists, because my "null only if the question names no listed type" outweighed a quiet "if there is one type, use it". It is now stated deterministically: with exactly one type the prompt says, by name, to use it whenever documents are counted, listed, summed or summarised. With several types a vague question is not forced onto one.
- **The eval had been able to score a wrong plan as right:** a `lookup` also returns a number, which can equal the expected count. `meta-plan-eval` now requires the plan to be the operation the fact asked for.
- **After the fixes** (fresh seeds 3, 4, 5, two questions per period shape): 24/24, 23/24, 27/28. The two misses are not planner errors: the question-phrasing model translated `order` (a decision) as "megrendelés" (a purchase order), so "no such type" was the right answer; and "az elmúlt héten" is "the past 7 days" in Hungarian where the eval expected the calendar week (the same kind of ambiguity as the earlier "elmúlt negyedév").
- **Also:** a one-off `499 CANCELLED` from the API aborted a run and did not recur on the next try; 499 is now retried like a 429 or a 5xx (`retry_policy.is_retryable_status`, one place for the rule, used by the answer and the Gemini embedding drivers). A real one-question-per-persona run through the router, with no document type configured, gave the same results as before.
- **Limits:** the type choice is exercised with a single type, so the multi-type behaviour is covered by tests and by a database test with two types (same key name `issuing_body` in both), not by a real second corpus; with many types the prompt grows (every type's keys), and a two-stage choice would then be needed.

## 2026-10-06 — A hung API request blocked an eval for 21 minutes: the SDK clients had no time limit

During the three-variant comparison one run (variant C) sat idle at 0% CPU for 21 minutes while the other two finished the same work in 7-9 minutes; its log had not changed since it started. It was not slow: it was waiting for an answer that never came. The `google-genai` clients (Gemini and Vertex, in `drivers/llm.py`) and the embedding `genai` client were built without any request timeout (the REST calls to the ranker and the embedding endpoints already had 60-90 s limits), so one lost response blocks the caller forever. The same would happen to a user's question. Restarting the run took 4 minutes.

- **Fix:** `API_REQUEST_TIMEOUT_SECONDS` (default 120) applies to every SDK client: Gemini, Vertex, the OpenAI-compatible ones and the embedding `genai` client. The `google-genai` SDK takes the limit in **milliseconds** (`HttpOptions(timeout=...)`, checked against the installed 2.25.0), the OpenAI SDK in seconds; a test uses a 7-second limit so a unit mix-up would show. A timeout raises `httpx.TimeoutException`, which `_generate` already turned into a retryable `TransientAPIError`: that path existed, but nothing ever fed it a timeout.
- **Proved on the real driver, not only on the constructor argument:** a local server that accepts a connection and never answers; the real `GeminiAnswerDriver` with a 1-second limit gave up after 9.2 s (3 tries of 1 s plus the 2 s and 4 s back-off), the server saw 3 connections, and `TransientAPIError` was raised instead of blocking.
- **The eval now prints a line per finished run** (`[3/10] q0011 done in 14s`, flushed): its report only appears at the end, so without progress a hung run looks exactly like a slow one.
- **Not done:** the per-question retry in the eval still raises after three failed questions and aborts the run (accepted: with a timeout a hang becomes a bounded failure instead of an endless wait); 120 s is generous for a grounded answer but a very large document summary could need longer, in which case the setting is the knob.

## 2026-10-05 — Restricted retrieval is a sub-select on a numeric document id, not a list of hashes (and the planner picks the right scan by itself)

The router restricted a retrieval with a *list* of up to 5,000 content hashes (`LOOKUP_SET_CAP`); more matches were refused ("too many, narrow the question"). A list cannot express "the 800,000 invoices of 2024", and it shipped ~320 KB with every query. Now the plan compiler also emits the matching documents as a sub-select (`models.DocumentSelection`: `SELECT d.id FROM documents d WHERE <the filters>` plus bound parameters) and `VectorStore(selection=...)` puts `document_id IN (<sub-select>)` in the vector, full-text and identifier searches. The cap and the refusal are gone; a `lookup` plan only counts its documents (for the "+K unknown" note and the "no documents match" answer). Built on the numeric `documents.id` / `document_chunks.document_id` of migration 0005 and the ingest change that sets it (commit 875ae62); the earlier entries about `content_hashes` describe the superseded form.

**Measured on the real data (2,235 documents, 55,038 chunks; the query vector is a real chunk's own embedding; read-only):**

| filter | documents | database's plan | time |
|---|---|---|---|
| none / one large court | 2,235 / 629 | HNSW index (approximate) | 4-5 ms |
| court + one year | 183 | `document_id` index + exact sort | 48 ms |
| court + one month | 19 | same, exact | 3.5 ms |
| case-number prefix | 140 | same, exact | 23 ms |

- **Same results, or better.** On four of five filters the top 10 was identical to the old list-based search. On the fifth the two differed, and against a brute-force exact search (index off) the *new* one matched 10 of 10 and the *old* one 8 of 10: the old form always went through the approximate HNSW index with a filter and missed two. The reason is not something we wrote: for a selective filter the database chooses the `document_id` index and an exact sort over just the selected chunks, and for a broad one the HNSW index. (An earlier hunch that the sub-select might push the database onto a slow sequential scan was wrong for this data; it was worth measuring.)
- **Caveats that must not be forgotten.** (1) The planner decides from statistics, so run `ANALYZE` after a bulk load or the migration back-fill (done here). (2) At much larger scale a "selective" filter can still mean hundreds of thousands of chunks, and an exact sort of those is slow; the choice between exact and approximate then needs re-measuring. (3) The match and unknown queries still join `document_meta` by `content_hash`; they move to `document_id` in the contract migration. (4) One query vector and five filters is a sanity check, not a benchmark.

## 2026-10-04 — Milestone 5: the router, and what it does when it is unsure

`query_knowledge_base` can now ask the planner first (`QUERY_ROUTER`, off by default; `query/router.py`). Unit-tested with fakes and the document restriction tested on a real Postgres; **not yet measured end to end**.

- **Restricting the retriever by document set is a property of the store, not a new parameter on every function.** `VectorStore(content_hashes=...)` applies `content_hash = ANY(...)` (the indexed generated column) in the vector, full-text and both identifier searches, so the strategies, the reranker and the answer step are untouched. An *empty* restriction sees nothing (it must never mean "everything"), and a restricted vector search turns on `hnsw.iterative_scan`, for the same reason the year filter does (HNSW applies WHERE after its nearest neighbours).
- **An identifier in the question skips the planner.** A case number is a pinpoint lookup the pipeline already does well; asking a model to plan it would add latency and a way to go wrong. Count questions that name an identifier are therefore not counted; accepted.
- **Exact answers are phrased by an LLM that may not change a figure.** The count, the unknown count, group counts and the sum's integer part must appear in the phrased answer (thousands separators ignored); if one is missing the plain facts are returned and a warning is logged. The executed filter is always echoed.
- **Nothing is hidden.** "+K unknown" is stated; a lookup restricted by a filter says how many documents could not be checked; a part of the question no key covers is named "not applied" (the result is not narrowed by it); more than `LOOKUP_SET_CAP` matches is reported instead of silently truncating the document set; zero matches says so instead of reading everything.
- **A question the planner cannot interpret is refused plainly, not answered by plain retrieval.** This follows the earlier agreement (no silent fallback). The cost is real: if the planner fails on an ordinary content question the user gets "could not interpret" instead of the pre-router answer. The planner prompt makes `lookup` the natural class for content questions, and `meta-plan-eval` plus real use will show how often that happens; revisit with data (a disclosed fallback to retrieval is the likely alternative).

## 2026-10-04 — Milestone 4 of the structured-metadata layer: the planner fails loudly, and its eval is a measurement tool, not a feature

Built `LLMQueryPlanner` (`metadata/planner.py`) and `meta-plan-eval` (`corpus/commands/meta_plan_eval.py`); **not yet measured** against a model.

- **No fallback plan.** A reply that is not JSON, or a plan the catalog rejects, is retried exactly once with the verbatim error; a second failure raises `PlanningFailed` carrying the reason and the last reply. A default plan (say, "count everything") would return a clean, confident, wrong number, which is worse than "I could not interpret this".
- **The planner validates with the compiler that will run the plan**, so a plan that passes cannot fail later, and the retry message is the same text a person would read.
- **The model never chooses the catalog** (`doc_type` is a caller argument) **and never does date arithmetic** (it describes the period in the closed grammar; the resolver computes it).
- **The eval's expected answers are computed in Python from the stored values, independently of the compiler**, otherwise a compiler bug would grade itself correct. It therefore measures planner + compiler, not extraction (`meta-accuracy` does that). It must be run on full extraction coverage, because a document without a stored value cannot match any question.
- **Questions are phrased by an LLM from a structured fact, on a fixed clock.** The first version used hand-written Hungarian templates with a month-name list: tied to one language, and with a narrow range of periods (nothing like "next week"). Now the code picks the fact (scope + period) and computes the exact answer in Python; an LLM only phrases it in the chosen language, and a phrasing that loses a required name (the court) is rejected and reported. Because the corpus is all past, relative periods ("next week", "last 30 days") would match nothing, so the eval runs on a fixed clock set to the median decision date and tells the planner that date. Trade-off: the same model phrases and plans, so a shared blind spot is possible (read the wrong cases, not just the percentage), and period arithmetic reuses the resolver (covered by its own calendar tests), so this measures whether the planner picked the right period description.
- **It lives under `corpus/`** because its question templates and Hungarian words are corpus-specific; the product capability is the generic planner/compiler/executor, wired into `query_knowledge_base` in milestone 5.

## 2026-10-04 — Milestone 3 of the structured-metadata layer: the plan, the date resolver, the compiler, and the rule that a count says what it could not decide

Built, with no LLM anywhere: `DateRangeResolver` (a small closed grammar -- absolute, calendar, relative, rolling, between -- resolved from an injected `Clock`), `parse_plan` (a strict shape check: unknown fields rejected, the doc type comes from the caller and never from the model), `PlanCompiler` (plan + catalog -> parameterised SQL) and `PlanExecutor`.

- **Dates are resolved in code, not by the model.** "Last October" is `{"kind": "calendar", "year_offset": -1, "month": 10}`; with today = 2026-10-04 that is 2025-10-01..31. Weeks run Monday-Sunday (so on a Sunday "next week" starts tomorrow), a rolling "last 30 days" includes today, a month shift clamps to the target month's length. `SystemClock` takes an explicit time zone (default Europe/Budapest): just after midnight "today" differs between Budapest and UTC and "next week" would be a day off. Ruff's `DTZ011` rule flagged the naive `date.today()`, correctly.
- **The compiler never puts a value in the SQL.** Values, key names and LIKE patterns are bound parameters; the only spliced text is a fixed fragment from a closed set (an operator, a column). Everything is checked against the catalog first (key exists and is *approved*, operator fits the type, a categorical value is an allowed token). The executor additionally runs in a **read-only transaction with a statement timeout** as defence in depth; tests show a `DELETE` is refused and a `pg_sleep` is cancelled, and that a `'; DROP TABLE documents; --` value is just data.
- **A count carries what it could not decide.** Besides the exact matching set the compiler builds a second query for documents that *might* match: for every filter, "satisfied OR the key is not known for this document at the key's current version", and not all satisfied. A document whose date was looked for and found absent, or whose court is known to be another, is *not* unknown; one whose date was never attempted or is unverified is. Bumping a key's version therefore makes all older extractions unknown again until they are redone. The answer must read `count` as "plus up to `unknown`".
- **A grouped count's total is its own query.** The groups need not add up to the number of documents (a multi-valued key, or a truncated group list), so summing them would be wrong.

Verified on a real Postgres with a seeded world: the opening question (a court's decisions last October: 2, unknown 0), both end days included and the day before excluded, truncated lists with the exact total, sums, groups, text/number operators, the unknown accounting above. Not yet: an LLM planner (milestone 4) and the wiring into `query_knowledge_base` (milestone 5).

## 2026-10-04 — The pipeline cannot count or list; a structured filter can (decisive experiment), and what that experiment did not prove

Counting/listing questions ("how many judgments in March 2022 at court X", "list ...") cannot be answered by top-k chunk retrieval. A throwaway experiment (not in the repo) measured both routes. **Part A**: 30 count questions (10 year-level, 10 month-level, 10 month + decision type) with exact ground truth (the signature-line date; `corpus/meta.csv` court and decision type, used *only as measurement truth* because it is a by-product of this corpus's downloader and must not enter a generic core), against an SQL filter on `document_date` with a perfect "planner" (the generating parameters). SQL: precision 94-100%, recall 98-100%, exact count on 7/10, 9/10, 9/10; the misses are +-1-2 documents out of ~200 caused by the ~0.4% wrong `document_date` values (see the entry below). The current pipeline gave the exact count on **0/8** (seven refusals or no number, one answer that was just the year). 55 documents have no `document_date` (23 of them at one court), so every count must say "N, plus K with no date".

**Part B**: 14 overview questions, filtered set's summaries in one LLM call vs the pipeline: the sweep cited on average 110 documents vs 2.1, and the pipeline's citations satisfied the question's court/year in only 8 of 29 cases. **Not proven**: the sweep's own "validity" (1,547/1,547) is true by construction (it only saw filtered documents); topical correctness and the truth of its claims were not measured; the 400-document cap cut the set in file-name order, not by relevance; `looks_like_a_decline` also flags partial answers, so the pipeline's refusal count is unreliable; some sweep answers were data dumps (288-302 cited documents), where a grouped count (a categorical key with GROUP BY) is the right shape; and an identifier question (q0018) did badly with the sweep, i.e. identifier lookups must stay on the lookup path.

**Direction (agreed with the user).** Build a generic structured-metadata layer, in this order: a `documents` table keyed by `content_hash` (re-ingest deletes chunks, so a chunk-id foreign key would go stale) + a key/value `document_meta` with evidence, a source tag (deterministic / LLM / sidecar) and an explicit "unknown" state; a JSON query-plan DSL compiled to parameterised SQL (no LLM-written SQL); date ranges resolved by a deterministic resolver from an injected clock (questions say "last October"). **The core knows nothing about any corpus**: corpus-specific knowledge lives only in catalog data, optional adapters (e.g. the existing regex date extractor, a sidecar importer) and the `corpus/` measurement tools.

## 2026-10-04 — How far to trust `document_date`: measured against the signature line and `corpus/meta.csv`

Before building year-based filtering or counting on `document_date` (the date regex-extracted from the last 500 characters of a document), checked it against two other sources over all 2,235 ingested documents. The reference is the **signature line** ("Budapest, 2021. december 14. ... bíró"), found in 1,932 documents.

- `document_date` year == signature-line year: **1,924 / 1,932 (99.6%)**; 8 wrong.
- `corpus/meta.csv` `year` (the downloader's metadata for all 10,492 files): == signature year 1,921 (99.4%), **exactly +1** in 8 (it looks like the publication / "Leírva" year, not the decision date), 3 other. `meta.csv` `court` equals the file-name prefix for 2,232 / 2,232 documents.
- The two sources' years differ for 20 documents (0.9%); `document_date` is NULL for 58 (2.6%).

**Why `document_date` is wrong in 8 cases:** `extract_document_date()` takes the *first* date in the last 500 characters; when a date is mentioned in the text just before the signature (e.g. a referenced "2023. január 1."), that one wins over the signature line. **Why 58 are missing:** none of them has a standard "Place, date" line -- some are anonymised templates ("Helység, dátum.", "eljáró bíróság székhelye, év. hónap nap."), some use a written form the regex does not know ("2021. év február 18. napján", "2024. év május hó 22. napján"; recoverable), some end without a date.

**Consequences.** At year level `document_date` is trustworthy (99.6%), but any count over it must report the 58 unknown dates ("N, plus K with no date"); `meta.csv` (a by-product of this corpus's downloader, so corpus-specific) carries a year that is not the decision date (publication lag); it is a useful *ground truth for measurement* in `corpus/`, and at most an optional, separately-sourced adapter -- never part of a generic core, and never merged into `document_date` silently. Two cheap deterministic fixes are available and **not yet done** (not urgent at 99.6%): prefer the signature-line date over the first date in the tail, and recognise the "év ... hó ... napján" form; both need a backfill over existing chunks, no re-embedding.

## 2026-10-04 — Broad questions were refused although relevant excerpts existed; the answer prompt, not retrieval, was the lever (and the grader had been deflating `independent_fact`)

**The symptom.** About 15 of 26 weak-persona golden questions ended in the fixed refusal sentence even though 2-4 documents were retrieved. The new `funnel` command showed that for q0010 the candidates were fine (13 of 17 documents met the question's court and years) and that the final 4 chunks came from only 2 documents; `top_k` 8 gave the same 2 documents. ## 2026-10-04 — A case number typed with different punctuation never reached its document (identifier match was literal)

Found by asking `make chat` "Miről szól a P.20487.2020.221 ügy?" about a document that is in the database: it refused. `extract_identifier_tokens()` recognized the token, but `search_by_identifier()` matched it with a literal `ILIKE` on the chunk text, and the document writes the same number as `4.P.20.487/2020/221` (a thousands dot in 20.487, slashes around the year), so the match returned 0 chunks, the identifier rescue never fired, and ordinary retrieval returned unrelated courts' cases -- an honest refusal on top of a retrieval miss. People write case numbers in many ways, so this is general, not one document's quirk.

**Fix**: besides the literal match, `search_by_identifier()` now also compares **separator-insensitively** against each chunk's stored `document_identifiers` (an array that 99.99% of chunks carry, e.g. `["4.P.20.487/2020/221-ítélet"]`): both sides reduced to lower-case letters and digits, with a non-digit required after the match so `...2020.22` cannot match `...2020.221`, and before it only when the token itself starts with a digit (a letter-initial token must still match inside the stored `4p...`, where `4` is the court-number prefix -- a first version had that leading boundary everywhere and would have rejected exactly this case; a unit test written against the real stored format caught it). Tokens that normalize to fewer than 6 characters, or contain no digit, get no loose match, so a short code like `HU001` cannot flood the results.

**Verified live**: the same question now retrieves exactly the one right document and answers correctly; `P.20487.2020.221`, `P.20.487/2020/221` and `P 20487 2020 221` all match, `P.20487.2020.22` does not.

**Not normalized (yet)**: the body-text match is still literal, so an identifier that appears only *inside* a document's text (not in its `document_identifiers`) is found only when written with the same punctuation; normalizing `content` itself means a full scan with a regex over ~2.4k characters per chunk, which is why it was not done blind.

## 2026-10-04 — Multi-document golden questions were failing because identifier guarantees let one long document take every `top_k` slot

Found by reading the golden-set eval's per-question retrieval misses (`corpus/cli.py eval --only-covered`): precedent_seeker/synthesizer retrieval hit was 0-38% while fact_finder/practical_procedural were 100%. Those weak personas' questions each cite 2 documents, and `exact_match` grading needs *both* in the final `top_k` chunks. The "rank 1" lines in the miss diagnostics looked like a ranking bug; they were just the question's *other* citation (the diagnostic prints every cited file, not only the missing one).

**Root cause (q0018, confirmed live and by a second-opinion read of the code):** a question naming two case numbers (both extracted correctly by `extract_identifier_tokens`) made `store.search_by_identifier()` run one `ILIKE ... OR ...` query with a single shared `LIMIT` and no `ORDER BY`. Since a document's identifier is embedded in every chunk, one long document (39 chunks) could fill all 20 rows and the second document none -- and which rows won was arbitrary. Then `_apply_top_k_with_guarantees` took `[:top_k]` of the guaranteed chunks by score, ignoring documents, so all 4 slots went to one document. A per-document cap on the non-guaranteed remainder alone would not have helped, because the guaranteed path fills the slots first.

**Fix** (`RETRIEVAL_DIVERSIFY_GUARANTEES`): `search_by_identifier(per_token=True)` gives each identifier token its own bounded, `id`-ordered share (`ROW_NUMBER() OVER (PARTITION BY ...)`); `_apply_top_k_with_guarantees(diversify=True)` fills guaranteed slots round-robin by document.

**Measured, not assumed** (`corpus/cli.py compare-retrieval`, retrieval-only, both arms in one process with a shared query embedding, 23 covered questions, ingest still growing the corpus): synthesizer hit 0% -> 20% (q0012, q0018: recall 0.5 -> 1.0), no question regressed, fact_finder/practical_procedural unchanged at 100%. **What this did not fix:** 18 of the 20 weak-persona questions are unchanged, many with 0.00 document recall. Those are content questions with no identifier ("in which cases did the court reject..."), where the correct documents never reach the candidate pool -- a separate recall problem. Candidates not yet tried: sending a `title` to the Vertex reranker, a larger `RETRIEVAL_CANDIDATE_POOL_SIZE`, a per-document chunk cap. Also noted: `_citation_ranks`' `pool=50` is 50 *chunks* (and wider than production's 20-candidate pool), so its "not found" is a weaker statement than it reads; not yet fixed.

## 2026-10-04 — Vertex answer driver kept hitting 401 because `google-genai` checks `credentials.expired`, not `valid`

Confirmed live: after the earlier fixes (`invalidate()` on a 401, and a `valid=False` override on `get_credentials()`'s credentials object), `GeminiAnswerDriver._generate` still retried on `Gemini generate_content status 401` -- the retries never recovered.

**Root cause**: `google-genai`'s `get_token_from_credentials()` decides whether to call `credentials.refresh()` from `credentials.expired or not credentials.token`; it never looks at `valid`. The `_GcloudCliCredentials` object never sets `expiry`, so the base class's `expired` is `False` forever -- the SDK took the first token and never asked for another, and `invalidate()` on a 401 had no effect because nothing re-read the cache. The earlier `valid=False` override was based on a wrong assumption about which property the SDK checks (verified this time by reading the installed SDK source).

**Fix**: `drivers/gcloud_auth.py` gained `is_stale()` (the cache's own freshness check, now shared with `get_access_token()`), and the credentials object's `expired`/`valid` are driven by it, so a near-expiry or invalidated token makes the SDK call `refresh()`, which re-fetches. Regression tests in `tests/unit/test_gcloud_auth.py`. Not verified against a real >1h Vertex session yet -- unit tests only.

## 2026-10-04 — `gcloud auth print-access-token` had no subprocess timeout; a real multi-hour bulk ingest hung indefinitely

Confirmed live: during the overnight full-corpus re-ingest, the ingest process went to ~0% CPU and made zero progress (no new `document_ingested` log entries, no new rows) for over an hour, after the user's terminal showed a 401 error. Diagnosed by checking `ps` (the process was alive, sleeping, not a crash) and the log timeline (real progress stopped abruptly, over an hour before the check). `drivers/gcloud_auth.py`'s `get_access_token()` calls `subprocess.run(["gcloud", "auth", "print-access-token"], ...)` with no `timeout` argument -- if that one subprocess call ever hangs (observed live, cause not fully isolated -- possibly a network hiccup mid-reauth after the preceding 401 invalidated the cached token), nothing bounds the wait, and every Vertex-backed driver's own `@retry_on_transient_error` never even gets a chance to fire, since it only retries on exceptions the decorated function actually raises -- an indefinitely blocked `subprocess.run()` call never returns at all.

## 2026-10-03 — CSLS hub-score re-ranking, document_summary enrichment, and listwise LLM rerank: three real techniques for the near-duplicate problem, plus the finding that q0030 itself wasn't fully a retrieval bug

Follow-up to the rejected boilerplate-exclusion filter above: a subagent research pass (web search, see its full report for citations) proposed three alternatives, all tested live against the same hard case (q0030, 19 real near-duplicate administrative-review judgments competing with the correct target).

**1. CSLS (Cross-domain Similarity Local Scaling) hub-score re-ranking** -- implemented and kept. `store.VectorStore.compute_hub_scores()` precomputes each chunk's average cosine similarity to its nearest `HUB_SCORE_NEIGHBOR_SAMPLE_SIZE` neighbors in the whole corpus ("hubness"/genericness), stored as `metadata.hub_score`. `query.retrieval._csls_rerank()` re-sorts the dense candidate pool by `2*raw_score - hub_score` before RRF fusion -- only ever changes *order*, never excludes a chunk, which is exactly why it doesn't repeat the boilerplate filter's failure mode. Confirmed live: moved the target from rank 16 to rank 6 of 19 in an isolated test, and from rank 19 to rank 9 of 20 in the real end-to-end pipeline. This directly replaces the rejected `BOILERPLATE_*` settings/`flag_boilerplate_chunks()`/`is_boilerplate` mechanism (all removed).

**2. `document_summary` chunk enrichment** -- implemented and kept, but confirmed to be a *modest* contributor on its own (rank 16→13 in isolation), not a solo fix. `ingestion.summarize.generate_document_summary()` makes one LLM call per document at ingest time, explicitly prompted for the document's own case-specific distinguishing facts (not a generic topic restatement -- confirmed live, again, that a generic summary just makes near-duplicates more alike, same lesson as the rejected Contextual Retrieval test earlier today). Embedded into every chunk's content via the same "outermost prefix" mechanism as `document_identifiers`, with matching strip functions for `SplitOverflowStrategy`. New settings `GENERATE_DOCUMENT_SUMMARY` (default `True`) / `DOCUMENT_SUMMARY_MAX_CHARS`; disabled in `.env.test` since it's an extra real LLM call `tests/db/` doesn't need. **Caveat discovered live**: testing it on only a subset of an otherwise-un-enriched corpus is actively misleading -- the enriched subset's chunks cluster together (sharing the same embedded prefix) and crowd out *everything else*, including the real target, purely because they're enriched, not because they're more relevant. A fair test requires a consistently-enriched corpus (confirmed by flushing and re-ingesting only the 19-document hard-case pool, all enriched, and re-testing cleanly).

**3. Listwise LLM rerank** -- implemented and kept (opt-in, `LISTWISE_RERANK_ENABLED`, default `False`, one extra LLM call per query). `query.listwise_rerank.listwise_rerank()` shows the LLM every remaining candidate document's `document_summary` side by side, explicitly instructed to ignore shared/formulaic framing, and picks one -- a disambiguation a per-pair cross-encoder structurally cannot do (it never sees that 19 candidates share the same template). Confirmed live on the clean 19-document pool: the LLM did **not** pick the golden document -- it consistently (3/3 runs) picked a different real document (`K_700143_2022_30`) instead of the golden one (`K_700539_2022_44`).

**This "miss" turned out not to be a retrieval bug.** Reading both documents' summaries side by side: both genuinely describe the court annulling the actual expropriation *határozat* (not a procedural *végzés*, e.g. an expert-fee ruling) and ordering a new procedure -- just for different underlying reasons (an unsubstantiated valuation vs. missing zoning documents). The question ("Milyen ügyben mondta ki... hogy a kisajátítás tárgyában hozott közigazgatási határozatot meg kell semmisíteni és új eljárást kell lefolytatni?") doesn't name anything that distinguishes the two at the *content* level, not just the lexical level -- confirming the subagent research's point 0 (check whether the question is underspecified before changing the retriever) more strongly than the morning's lexical check did. Ran the real generated answer (citing `K_700143`) through `IndependentFactGradingStrategy.grade()` directly: **`answer_correct: True`, `citation_correct: True`** -- the strategy built earlier today specifically to accept any content-verified answer, not just the golden one, correctly recognized this as a genuinely correct answer. `precedent_seeker`'s existing dual-strategy grading (`exact_match` + `independent_fact`, see the GradingStrategy entries above) already does the right thing here without any further change: `exact_match` would fail this case, `independent_fact` passes it, and that's the honest, correct split -- not a bug in either direction.

**A caution about the listwise-rerank validation itself**: the prompt used to *validate* this technique earlier today (a one-off manual test, not the shipped `_PROMPT_TEMPLATE`) explicitly told the LLM the specific distinguishing legal concept to look for (*határozat* vs. *végzés*) -- which guaranteed it picked the golden document in that one test. The shipped, domain-agnostic prompt (deliberately generic, no hardcoded legal concepts) doesn't get that hint, and without it, this is a genuinely hard disambiguation that doesn't always land on the golden document -- which, per the paragraph above, isn't actually a problem, since "genuinely hard disambiguation with no single determinable answer" is exactly what `independent_fact` grading exists for.

**State left after this session**: the local DB was flushed and currently holds only these 19 hard-case documents (re-ingested with `document_summary`, hub-scored) -- deliberately, to get a clean test free of the enriched-subset-crowds-out-everything-else confound above. The full corpus re-ingest (with the embedding model switch, `hungarian` FTS, `document_date`, the identifier-flooding fix, and now `document_summary`, all bundled) is still pending.

## 2026-10-03 — reordered prompt context so the best-ranked chunk sits right before the question ("lost in the middle")

Checked a candidate fix from the NotebookLM research review: LLMs attend most to the very start and end of a long context and lose track of content in the middle. `drivers/llm.py`'s `_build_prompt()` was building the numbered context block in `context_chunks`' own order -- best-ranked chunk first, worst-ranked last, immediately before "Question:". That puts the single most useful excerpt in the *weaker* of the two high-attention positions and the least useful one in the stronger position (right next to where the model is about to answer).

**Fix**: `_build_prompt()` now iterates `reversed(context_chunks)`, so the block reads worst-to-best and the top-ranked chunk ends up last, right before the question. The `[i]` labels follow display order, not original rank -- confirmed safe, since citation verification (`corpus/commands/eval.py`'s `_resolve_cited_source_files`) extracts identifiers from the answer's own text, never from these index labels.

## 2026-10-03 — fixed identifier-rescue context flooding; `_apply_top_k_with_guarantees()` now caps guaranteed chunks too

Diagnosed while investigating an apparent `practical_procedural` regression: `q0002` retrieved the exact right (and only) document for its case number, yet the LLM declined to answer. Root cause: the document-identifiers-in-every-chunk fix (see the 2026-10-02 entries below) means a single cited case number now makes `store.search_by_identifier()` match an entire document's ~20+ chunks, not just the one chunk that originally carried the header -- all of them "guaranteed" by `_apply_top_k_with_guarantees()`. That function's own docstring already documented the consequence as a deliberate tradeoff ("more than `top_k` only if there are more guaranteed chunks than `top_k` itself") -- a reasonable assumption back when identifier matches were rare (one chunk), invalidated once identifiers started being embedded into every chunk. Confirmed live: `search_by_identifier()` returned 23 chunks for one case-number query; the resulting bloated, repetitive context made the LLM respond as if it couldn't find the information, even though retrieval had done its job correctly.

**Fix**: `_apply_top_k_with_guarantees()` now caps the guaranteed set at `top_k` as well, same as everything else -- `guaranteed = [...][:top_k]` instead of letting it through unbounded. Since `chunks` arrives already reranked in descending-score order, this still keeps the highest-cross-encoder-scored chunks of the matched document first, it just no longer lets *all* of them through regardless of count. The two existing regression tests for this function's original purpose (survive `top_k` truncation, survive the reranker threshold gate) still pass unchanged, since both only ever exercised a single guaranteed chunk.

## 2026-10-03 — adopt `hungarian` full-text search config, pending next re-ingest (decided, not yet implemented)

Raised by the same NotebookLM research review as a candidate fix: `search_fulltext()`'s `content_tsv` column is built with Postgres's `simple` tsvector config (no stemming), which means a question using one Hungarian inflected form of a word ("alperesekkel", instrumental+plural) never matches a chunk using a different inflected form of the same word, even though they're the same legal concept. Tested live, not assumed: 5 fact_finder/practical_procedural questions (case numbers stripped out, since those are rescued separately via `search_by_identifier()`'s `ILIKE` match, not FTS), ranking the real target chunk among ~3000 FTS-matched chunks under `simple` vs. Postgres's built-in `hungarian` (snowball stemmer) config.

Result was directionally positive but mixed: average target rank improved (269 → 214 across the 5 questions), 3/5 improved and 2/5 got worse, and one case (q0008) crossed a threshold that actually matters in production -- `simple` ranked its target chunk at 334 (well outside `RETRIEVAL_CANDIDATE_POOL_SIZE=20`, so the keyword search alone would never have surfaced it for RRF fusion), `hungarian` ranked it at 5 (comfortably inside). The other 4 questions' ranks stayed far outside the top-20 either way, so for them this config choice doesn't change the final retrieval outcome -- only the vector/identifier-rescue path does.

**Decision**: adopt `hungarian` for `content_tsv`. No further dedicated A/B needed before committing to it -- it's a cheap, reversible config change with zero risk to identifier matching (a separate, non-FTS code path), and the full golden-set eval that runs around the next re-ingest will validate it with real numbers at full scale anyway, which a 5-question sample can't substitute for.

**Implemented**: `migrations/0003_hungarian_fulltext_search_config.py` drops and re-adds `content_tsv` with the `hungarian` config (Postgres doesn't support altering a generated column's expression in place), and `store.py`'s `search_fulltext()` query-side `websearch_to_tsquery` calls were updated to match -- both sides of a tsvector/tsquery comparison must use the same config, or stemmed lexemes on one side simply won't match unstemmed ones on the other. Applied locally; took ~142s to regenerate across 81K existing rows plus the GIN index.

## 2026-10-03 — mean-centering embeddings ("subtract the shared boilerplate component") rejected; slightly worse (no code change)

Tested whether near-duplicate boilerplate leaves a shared "common component" in the vector space worth removing: subtract the mean vector from both query and chunk embeddings, re-normalize, re-rank. It can detect regressions but has almost no room to show improvements, so it's a weak instrument for judging *any* further retrieval change. ## 2026-10-03 — document date/location: metadata column, not embedded chunk header

Also raised by the same review, while discussing what else to add to the chunk header (alongside the already-shipped case-number fix) before the next ingest: should the document's date ("kelt ideje") and place of issue ("kelt helye") go into the embedded chunk text too? Decided no, for the opposite reason the case-number header fix was worth doing.

The case-number header fix was justified because `search_by_identifier()` does a literal `ILIKE` substring match against chunk *content* -- the case number had to be in the text for that lookup to work at all. A date has no such requirement: it's needed as a *filterable* field (court, year, date range) and as *context fed to the answering LLM at query time*, neither of which requires it to live inside the embedded vector. Putting it there would actively hurt: every chunk of every document would gain a few words of near-identical formatted text ("Budapest, 2022. május 12."), pulling the vectors of already near-duplicate boilerplate documents even closer together -- the opposite of what's needed for the near-duplicate-dilution problem this session has been fighting all day. It would also dilute a 250-word chunk's already-scarce distinguishing content, and a substring match on a date is fragile anyway (format varies: "2022. május 12." vs. "2022.05.12."), unlike the case-number lookup it was modeled on.

**Decided placement instead**: a nullable `document_date` (and `court`, already partially present) column in `document_chunks`' metadata, queryable via SQL filter -- not embedded. Named `document_date`, not `decision_date`: the corpus today is all court decisions, but the field shouldn't bake that in, since nothing about the pipeline (extractor, chunker, metadata) is actually specific to court decisions -- a future non-decision document (a contract, a filed motion) still has a date of issue, just not a "decision." Place of issue was judged mostly redundant with the court name itself (it's almost always the court's own seat) and not worth a separate field. Formatted chunk-header text assembled from this metadata at *query* time (for the answering LLM's prompt, and optionally for reranker input) remains fine, since only the embedding step is sensitive to boilerplate dilution.

**The column must store a normalized date (SQL `DATE`, ISO-8601), not the raw matched text.** The corpus already mixes at least two written formats for the same date ("2022. május 12." vs. "2022.05.12."), and a free-text field would just push the fragile-substring-match problem (the exact reason this isn't going into the embedded header) one step downstream, into every `WHERE document_date = ...`/range filter instead of into `search_by_identifier()`. Extraction has to parse whichever format it finds (including the Hungarian month name) into a real date before storing it, so every filter/sort downstream is comparing actual dates, not strings.

**Implemented**: `ingestion/chunker.py`'s `extract_document_date()` (regex, both written formats, scanned from the document's *tail* rather than head) now populates `models.ChunkMetadata.document_date` for every chunk via `chunk_document()`, confirmed via tests to attach to every chunk's metadata while never being prepended to chunk content. Falling back to the case number's year when the date itself is missing (the ~10% gap) is not built -- deferred until real post-re-ingest numbers show whether it's worth it.

## 2026-10-03 — Added a Strategy-based GradingStrategy for category-style golden questions; found a much bigger, unrelated bug while validating it (pending commit)

**The methodology problem**: `precedent_seeker`/`synthesizer` questions ask about a *category or pattern* of case (e.g. "which cases involve X type of ruling"), and their own `citation_expectation` in `personas.json` already says "one or more... based on content/legal pattern, not region" -- not a fixed pair. ## 2026-10-02 — Built the deferred identifier-in-every-chunk-header fix; found a separate DOCX header/footer extraction gap along the way (pending commit)

Implements the fix deferred in the 2026-09-30 entry below: a document's case number used to only get embedded into whichever chunk happened to contain the document's header line (`chunk_index=0`), so `store.search_by_identifier()` could rescue that one chunk but nothing deeper in the same document — `retrieval_hit_rate` checks at the document (`source_file`) level, so this gap could be silently masked even after the identifier-rescue fixes.

**New**: `ingestion.chunker.extract_document_identifiers(full_text, head_chars=100)` — reuses `store.extract_identifier_tokens()`'s document-type-agnostic token recognition, restricted to the document's first 100 characters. Found and fixed one real bug while writing the regression tests: `_package_chunk()`'s idempotency check (skip re-embedding if the identifiers prefix is already present) used `content.startswith(prefix)` instead of `content.startswith(f"{prefix}\n\n")` — for a document whose chunk 0 happens to literally start with its own case number inline (e.g. `"103.K.703.261/2020. felperes..."`), this loose check matched the bare identifier substring and incorrectly skipped embedding the real `\n\n`-delimited prefix format, silently leaving chunk 0 unrescuable by the exact mechanism meant to fix that.

## 2026-09-30 — Deferred: bake each document's identifier into every chunk's header, not just chunk 0

While discussing the identifier-rescue fixes above, a real gap surfaced that today's fixes don't address: a document's case number typically only appears once, near the top (`chunk_index=0`) — `search_by_identifier()` can only find *that* chunk via an exact match, not a different chunk deeper in the same document that might hold the actually-relevant content (e.g. the court's reasoning, several chunks in). The fix would mirror the header-enrichment mechanism `ingestion/chunker.py` already uses for Markdown/DOCX section breadcrumbs (`header_path`): extract each document's identifier once during ingestion and prepend it to every one of that document's chunks, not just the first, so an identifier-based query-time lookup can find whichever chunk actually has the relevant content, not just the header chunk.

**Deliberately not built now**: unlike today's other fixes (all query-time, applied against the already-ingested corpus), this needs an *ingestion*-time change — every already-ingested document (1000+ and growing, still mid-ingestion as of this session) would need to be re-chunked and re-embedded to pick up the new header. Worth doing, but as a deliberate, separate decision once the current ingestion run finishes, not a mid-flight interruption of it.

Immediate follow-up to the identifier-rescue fix below, found by re-running the golden-set eval after marking `q0011`/`q0012` reviewed: `q0002` (`practical_procedural`) still scored a retrieval MISS despite citing a case number that `extract_identifier_tokens()`/`search_by_identifier()` correctly found. **Scope note, discussed explicitly and confirmed still correct**: this mechanism (`extract_identifier_tokens`/`search_by_identifier`/the guarantee) remains fully document-type-agnostic by construction — nothing in it references court decisions, case numbers, or legal terminology. `_is_inflected_number()` is the one narrow exception, and it's a Hungarian-*language* quirk (numbers with attached grammatical suffixes like "2020-as"), not a document-*type* specialization. First live run of `corpus/cli.py eval` against the seed golden set immediately did what it was built for: surfaced two real, distinct bugs, not just a "score." One in the RAG pipeline itself, one in the golden-set generation tooling.

**Bug 1 (real, in `query/retrieval.py`): exact identifiers lose to common words in hybrid search's ranking.** `fact_finder` question q0001 asked about a specific case (`4.P.20.409/2023/4`) and scored a retrieval MISS. Investigated live, not assumed: confirmed the correct document's raw cosine similarity (0.8847) sat *below* 10+ other documents (0.8997–0.9053) sharing near-identical legal boilerplate ("a bíróság a felperesek keresetét elutasítja") — vector search alone can't distinguish this specific ruling from dozens of structurally similar ones. A token counts as identifier-like if it mixes letters+digits, contains a separator (`.`/`/`/`-`), or is a pure number 5+ digits long (long enough not to just be a year) — refined once more after a real false positive: "2020-as"/"2022-es" (Hungarian "of 2020"/"of 2022") matched the digit+separator rule and, being extremely common, flooded `search_by_identifier`'s result limit ahead of the real case numbers in the same question. Verified live: q0001 now hits.

## 2026-09-30 — Fixed Gemini drivers not retrying network errors (pending commit)

Found live, mid-way through the first full 10,491-document corpus ingestion: a transient WiFi drop (`httpx.ConnectError: [Errno 65] No route to host`) crashed the entire `add_directory()` run instead of failing just the one in-flight batch. Root cause: `GeminiEmbeddingDriver._embed_one_batch()`/`GeminiAnswerDriver._generate()` only caught `google.genai.errors.APIError` (Gemini's own API-level error type, e.g. a 429/5xx *response*) — but `google-genai` uses `httpx` internally, and a connection-level failure (DNS error, no route, timeout) raises `httpx.TransportError`, a completely unrelated exception hierarchy that was never retried at all and isn't an `OSError` subclass either, so `ingestion.ingest.add_directory()`'s per-file `except (..., OSError)` didn't catch it as a per-file failure — it propagated all the way up and killed the whole run.

This is the exact same class of bug `OpenRouterEmbeddingDriver._embed_one_batch()` already handles correctly via `except requests.RequestException` — missed when the Gemini drivers were built, since the earlier testing sessions never happened to hit a real network blip mid-run. Fixed by also catching `httpx.TransportError` in both Gemini call sites and raising it as `TransientAPIError`, so a transient connectivity blip now retries with the same exponential backoff as a 429/5xx, instead of crashing a many-hour ingestion run over a few dropped seconds of WiFi. Added `httpx` as an explicit direct dependency (`uv add httpx`) rather than relying on it staying available transitively via `google-genai` — now that first-party code imports it directly and depends on its exception types, that dependency should be visible in `pyproject.toml`, not implicit.

## 2026-09-29 — Deduplicated retry-with-backoff logic into `retry.py` via `tenacity` (`83e260b`)

By the time the native Gemini driver (below) was added, the same hand-rolled retry loop (manual `for attempt in range(...)`, `backoff_seconds *= 2`, per-call-site `time.sleep`) was duplicated three times: `OpenRouterEmbeddingDriver._embed_one_batch`, `GeminiEmbeddingDriver._embed_one_batch`, and `corpus/download_court_decisions.py`'s `request_with_retries()`. Flagged as not a good path to keep extending — a fourth caller would have meant a fourth copy.

Added `tenacity` (`uv add tenacity`) rather than hand-rolling a shared decorator: it's a well-established, actively maintained retry library, and none of these three call sites needed anything tenacity doesn't already do off the shelf. Considered `asyncio`-based retry/backoff instead, but rejected — nothing in this codebase is `async` (`grep -rn "async def\|asyncio"` across the project returns nothing), so that would have meant asyncifying every caller up the stack (drivers → ingestion → CLI) for no benefit over a synchronous decorator.

New `retry.py` (top-level, alongside `db.py`/`models.py`/`logger.py`) exports `TransientAPIError` (raised by a call site to mark a failure as retryable) and `retry_on_transient_error()` (a `tenacity` decorator factory: exponential backoff doubling from 2s, `reraise=True` so the original `TransientAPIError` propagates after the last attempt rather than a wrapped `RetryError`). `TransientAPIError` deliberately subclasses `OSError` — `ingestion/ingest.py`'s per-file `except (ValueError, FileNotFoundError, RuntimeError, OSError)` handling already existed before this change and needed to keep catching a retry-exhausted embedding failure without knowing about the new type; the driver previously raised `requests.RequestException`, itself an `OSError` subclass, so this preserves that behavior rather than silently introducing an uncaught-exception regression.

All three call sites were rewritten to raise `TransientAPIError` for a retryable condition (network error, 429, 5xx) and let any other exception propagate as-is (tenacity's `retry_if_exception_type(TransientAPIError)` only intercepts that one type) — `corpus/download_court_decisions.py`'s `request_with_retries()` keeps its existing external contract (returns `None` after exhausting retries, rather than raising) by applying the decorator to a small inner function and catching `TransientAPIError` at the outer function's boundary, since its `max_retries` is a CLI-configurable value rather than a fixed constant tenacity's decorator syntax can take at class-definition time.

## 2026-09-29 — Switched to `EMBEDDING_DRIVER=openrouter`; made `RERANKER_DRIVER=cross_encoder` the default (`ca9e225`)

Ingesting the real-estate-law corpus with the local embedding driver measured ~17.8s/document (10 real documents, 177.76s total) — projected to **~2 days** of continuous CPU-bound embedding for the full ~10,000-document corpus. Looked for a faster alternative before committing to that.

**`EMBEDDING_DRIVER=openrouter` was added** rather than a native Gemini SDK integration, after discovering (live, via `GET /api/v1/embeddings/models`) that OpenRouter already exposes `google/gemini-embedding-001` — reusable with the *same* OpenRouter account/key this project's `LLM_DRIVER=openrouter` already uses, no new provider account needed. Verified against the real endpoint, not assumed:
- Native output is 3072d, but OpenRouter's `dimensions` request parameter truncates it — confirmed working down to 384, this project's existing `document_chunks` column width, so switching needed **no schema migration** (helped by the table having just been flushed for this restart anyway).
- Real cost: `1.65e-06` per 11-token call ≈ **$0.15/1M tokens** ≈ **~$5 for the full corpus** — cheap enough not to be a real constraint.
- Real speed on 10 real documents (word chunking, see below): **55.7s total ≈ 5.6s/doc**, ~3.2× faster than local, projecting to **~15-16 hours** for the full corpus instead of ~2 days.

**Two real bugs found via the same live re-ingestion test, not by inspection:**
1. The API hard-rejects a batch over 250 items: `HTTP 400`, *"batchSize value of 300 but the supported range is from 1 (inclusive) to 251 (exclusive)"*. `OpenRouterEmbeddingDriver.embed_batch()` now splits into sub-batches of at most 250 automatically. Without this, any document producing >250 chunks in one `embed_documents()` call failed outright (3 of the first 10 real documents did).
2. This driver has no real tokenizer (`count_tokens()`/`max_sequence_length()` stay `None`, same as `openai`), and `.env` still had `CHUNKING_STRATEGY=langchain` from earlier local-driver tuning. Without a real tokenizer, `langchain` silently measures `CHUNK_SIZE` in raw *characters*, not words — one real document went from an expected ~15 chunks to **407**. Fixed by setting `CHUNKING_STRATEGY=word` for this driver, which needs no token counting at all.

**A more consequential finding, discovered while sanity-checking the relevance gate against the new model**: a real, obviously relevant Hungarian query scored **0.73–0.76** raw cosine similarity against real ingested content, which sounds fine against `RETRIEVAL_MIN_SCORE=0.25` — until a deliberately *irrelevant* Hungarian query (about frying chicken) also scored **0.54–0.55**, comfortably above the same 0.25 threshold. The `_passes_relevance_gate()` check (`query/retrieval.py`) is vector-only by design (see the README's "What happens when there's no reliable source" section) — with this embedding model, that gate alone can no longer reliably distinguish relevant from irrelevant queries. The threshold was tuned for the local e5 model's similarity scale; nothing guarantees it transfers to a different model's scale, and this is the first time this project actually swapped `EMBEDDING_DRIVER` on a populated index to find out.

**Decided against raising `RETRIEVAL_MIN_SCORE` to compensate.** The vector gate is a cheap, coarse, single-number threshold — tightening it risks rejecting genuinely relevant chunks that simply don't score well under raw cosine similarity (different phrasing, topically-adjacent-but-correct content), trading false negatives for false positives on too little data (two anecdotal queries) to calibrate responsibly. Real recalibration is deferred to the golden-set/eval work already planned, where there'll be enough labeled examples to tune against instead of guessing.

**Instead, re-tested with `RERANKER_DRIVER=cross_encoder` enabled** (previously not the default — see the 2026-09-26 "Cross-encoder logit calibration" entry). The reranker correctly rejected the irrelevant chicken-frying query (all candidates scored below `RERANKER_MIN_SCORE=-2.0`, correctly returning no results) while keeping the relevant query's chunks (logits 3.6–4.2). This works because the cross-encoder scores `(question, chunk)` *jointly*, not via embedding distance — its relevance judgment isn't tied to any particular embedding model's similarity scale the way the vector gate's threshold is.

**This made `RERANKER_DRIVER=cross_encoder` the new default** (`config.py`, `.env.example`), reversing the original `none` default from the 2026-09-26 entry. That original reasoning ("hybrid fusion is already a reasonable ranking on its own, reranking is optional") held for a single, fixed local embedding model — it doesn't hold once the embedding driver is something users are expected to actually swap, since nothing else in the pipeline then reliably catches an irrelevant query. `none` remains a real, selectable option for comparison/eval (`make eval` vs. the old bare-RRF baseline), just no longer the production default.

## 2026-09-29 — `RtfExtractor`: plain text only, header detection deferred; a real striprtf whitespace quirk (`0f00f1d`)

Second extractor for the real-estate-law corpus, after `DocxExtractor`. Unlike DOCX, RTF has no equally cheap way to get both clean text *and* paragraph-level formatting (alignment) in one library call: `striprtf` (the standard choice for RTF-to-text) discards all formatting, so replicating DOCX's centered-paragraph header signal would require a hand-rolled RTF parser reading `\qc`/`\pard` control words directly. Deferred deliberately rather than built speculatively — as of this decision, 0 of 5743 downloaded corpus documents are RTF, all are DOCX. `RtfExtractor` therefore matches `PDFExtractor`'s level of detail (plain text, no `header_path`), not `DocxExtractor`'s.

**A real library quirk, found via a real (unmocked) test, not assumed**: `striprtf` sometimes swallows the whitespace immediately following a hex-escaped character (`\'e9`), merging it with the next word (`t\'e9 l` → `"té l"`, not `"t é l"`). This only matters for letter-spaced text — which happens to be exactly the convention real corpus documents use for centered section titles ("í t é l e t e t :", see the `DocxExtractor` entry above) — but since `RtfExtractor` doesn't do header detection at all yet, it's a cosmetic spacing slip in body text today, not something anything currently depends on. Documented in the extractor's own docstring and a dedicated regression test, in case it matters once header detection is eventually added for RTF.

Also resolved along the way: RTF files declare their own character encoding via a `\ansicpg<N>` control word in the header — the raw file bytes are decoded as latin-1 first (a 1:1 byte-to-codepoint mapping that never raises, since RTF's control words are pure ASCII and non-ASCII characters are hex-escaped rather than embedded as raw high bytes), then `striprtf` interprets the hex escapes using whichever codec `\ansicpg` declares (defaulting to `cp1250` — Central European — since this corpus is Hungarian, for the rare case it's missing).

## 2026-09-29 — `DocxExtractor`: alignment, not heading styles, is the section-title signal (`977bb00`)

Building the ingestion side for the real-estate-law corpus (`corpus/download_court_decisions.py`), starting with `.docx` since 5555/5555 downloaded so far are DOCX, none RTF. ## 2026-09-29 — Chunk packaging: rejected `ProcessedChunk`/`ChunkPacker`, extracted a smaller fix (`64a3c75`)

Károly asked for a `ProcessedChunk` type (distinct from `Chunk`) and a `ChunkPacker`/`ChunkEnricher` component to own header-breadcrumb prefixing *and* token-budget enforcement, motivated by a real observation: `SplitOverflowStrategy.apply()` was reverse-engineering `chunk_document()`'s header-embedding format — stripping `enrich_chunk_content()`'s output back off via a string-prefix check — to re-split an already-packaged chunk without duplicating or double-counting its header. That coupling is real and worth fixing.

The two-part proposal was scoped down before implementing, for reasons that mirror the 2026-09-29 Clean Architecture entry below:
- **No `ProcessedChunk` type.** `Chunk` already *is* the packaged, embedding-ready shape — in `chunk_document()`, `Chunk.content` is already header-enriched. A second type with no new fields would just be `Chunk` under another name, working against the same day's minimal-model-set decision (see the Clean Architecture entry below, which introduced `models.py`).
- **No `ChunkPacker` owning token-budget enforcement.** That's already `ChunkOverflowStrategy`'s explicit, `.env`-selected job (`WarnOverflowStrategy` vs. `SplitOverflowStrategy`). Giving a second component that same authority would blur `WarnOverflowStrategy`'s whole point (warn, don't correct) and create two places that could disagree about whether a chunk fits.

What actually landed instead: `_strip_header_prefix()` in `ingestion/chunker.py`, written as `enrich_chunk_content()`'s explicit inverse and kept immediately next to it, plus `_package_chunk(content, metadata) -> Chunk` as the single place both `chunk_document()` and `SplitOverflowStrategy.apply()` go through to build a chunk — removing the implicit, unenforced format contract without adding a new type or a competing authority over the token budget.

## 2026-09-29 — Clean Architecture re-discussion: targeted fixes instead of a layered rewrite (`c91b35c`)

Károly proposed migrating to Clean Architecture (Entities/Use Cases/Interface Adapters/Frameworks, with a strict Dependency Rule) ahead of scaling up to the 10,000+ document legal corpus, explicitly as both a real concern and a hands-on learning goal. `AGENTS.md` already had a dated, considered rejection of DDD/layered ceremony for this project (2026-09-17) — the honest way to answer "should we revisit that" was to actually check the current code against the three concrete complaints (SOLID/SRP, OCP, DIP) rather than debate architecture styles in the abstract.

**What the code review actually found:**
- **SRP**: `agent.py`, `query/retrieval.py`, and `store.py` were already thin/focused — `store.py` in particular already *is* what the proposal called an "Interface Adapter/Repository," just not filed under that name. The one real hotspot: `ingestion/ingest.py`'s `add_document()` mixed real dedup/versioning business logic (skip-unchanged / alias-duplicate / replace-previous-version / insert-new, ~30 lines of branching) directly into what's supposed to be a thin orchestrator, and `add_directory()` had a near-duplicate of the same branching.
- **OCP**: already well served — the Strategy/Driver pattern runs across embedding, LLM, reranker, *and* retrieval strategy (4 independent hierarchies), plus the deliberately-different extractor dispatch. Nothing to extend here; the proposal's "can we extend this to extractors/vector-DBs too" question turned out to already be "yes, extractors already do."
- **DIP**: `ingest.py`/`retrieval.py` depend on a concrete `VectorStore` class, not an ABC. But there is exactly one backend (Postgres+pgvector) and no concrete plan for a second — a `VectorStoreRepository` ABC with one implementation would be the textbook premature abstraction this project's own top-level guidance warns against.

**The agreed compromise** (all three items delivered in commit `c91b35c`):
1. Extracted the dedup/versioning decision into a pure, unit-tested `_resolve_ingest_action()` (`ingestion/ingest.py`) — fixes the one real SRP hotspot, and as a bonus removes the near-duplicated branching between `add_document`/`add_directory`. See `AGENTS.md`'s "Orchestrator functions must stay thin" bullet.
2. Introduced typed `dataclass`es (`models.py`: `ChunkMetadata`, `Chunk`, `RetrievedChunk`) in place of the untyped chunk dict, motivated by the corpus's upcoming richer metadata (header paths, section breadcrumbs) making typo'd dict keys a real risk. Not a full Entity layer — no validation logic, no framework independence beyond what a plain dataclass already gives; Postgres JSONB storage unchanged (`to_dict()`/`from_dict()` are the only serialization boundary).
3. Deliberately did **not** introduce a `VectorStoreRepository` ABC — no second backend to justify it (see DIP finding above).

Explicitly NOT done, and why: no Entities/Use-Case/Interface-Adapter folder restructuring, no dependency-injection framework, no bounded contexts. ## 2026-09-29 — Corpus acquisition: reverse-engineered eakta.birosag.hu's search/download endpoints (`b157435`)

Built `corpus/download_court_decisions.py` to collect a large (10,000+ document), realistic real-estate-law corpus for the upcoming large-scale retrieval/answer-accuracy eval (profiled user questions, a golden set — see the RAG-accuracy-at-scale direction). No public API exists for the site's "Bírósági Határozatok Gyűjteménye" (anonymized court decisions), so the actual request shape was reverse-engineered from the page's embedded JavaScript (the "ENCO.Grid" component) and verified against live responses rather than assumed.

**Findings that shaped the script:**
- The search (`POST /AnonimizaltHatarozat/Search?Area=`) is a plain JSON API — no headless browser or HTML scraping needed, simpler than expected. Getting the request shape right took actual trial and error: the site's own JS builds `KeresoSzavak[]`/`KeresoSzoOperatorok[]` array params, and a wrong operator enum value (guessed as `"AND"`/`"OR"` before finding the real `KeresoSzoOperatorDropdown` options: `Osszes`/`Kifejezes`/`Pontos`) produces a generic, misleading "Hiba történt..." error with no indication of which field is wrong.
- The `HatarozatFajta` filter (Ítélet/Végzés) accepts exactly one value per search — getting both types requires two separate searches, deduplicated by `(court, case_number)` across all of them.
- **The "native format" download endpoint doesn't always return RTF** — it returns whichever format the source court originally filed in, RTF *or* DOCX, with the real format only knowable from the response's `Content-Type`/`Content-Disposition` headers, not assumable from the request. The script reads this back per-download rather than hardcoding an extension.
- Inspecting a real DOCX/RTF pair showed neither uses Word "Heading" styles for section titles (e.g. "ÍTÉLET", "INDOKOLÁS") — the actual convention is a **centered, letter-spaced paragraph** (`w:jc="center"` in DOCX, `\qc` in RTF), confirmed identically in both formats for the same section marker. This is a cheap, reliable, markup-level signal — unlike PDF, which would need coordinate/font-size heuristics for the same job — and is the planned basis for a future header-enrichment pass on this corpus, analogous to the Markdown extractor's `header_path` (see the 2026-09-27 entry above), once ingestion-side RTF/DOCX extractors exist.

**Resume-safety, added after being asked directly "what happens if this gets interrupted":**
- File writes are atomic (write to a `.part` temp file, then rename) — a crash/power-loss mid-write can never leave a truncated file that a later run would mistake for a complete download.
- `meta.csv` is append-only and a re-run only treats a `(court, case_number)` as done if its *latest* recorded status is `downloaded`/`already_downloaded` — a row left at `error` (e.g. from a transient network outage) is automatically retried on the next run instead of being skipped forever.

## 2026-09-19 — MCP server: five real bugs found integrating with a real host (`fb5af0a`)

Found by testing `mcp_server.py` against a real MCP client (Claude Desktop), not by inspection or reading the SDK's docs alone:

1. `ingestion/ingest.py`/`query/retrieval.py` used to report progress via `print()`. Over MCP's stdio transport, stdout is reserved for the JSON-RPC protocol — a stray `print()` line landed on that channel mid-call and broke a real client's message parsing (`Failed to parse JSONRPC message from server`), confirmed by spawning `mcp_server.py` as a real subprocess and calling both tools over the actual protocol. Fixed by switching both modules to Python's `logging` module (stderr by default, invisible to the protocol stream) — `agent.py`/`scripts/eval_cli.py`/the `make add-document`/`query` targets configure a bare `logging.basicConfig(format="%(message)s")` so their own CLI output looks exactly as before.
2. `uv run mcp install`'s own generated launch command (`uv run --with "mcp[cli]==X.Y.Z" mcp run <path>`) is built for a standalone, dependency-free single-file script — the SDK's own docs say so explicitly. `mcp_server.py` isn't that: it imports the whole project (`psycopg2`, `openai`, `sentence-transformers`, ...). Registering it as-is and launching from Claude Desktop failed immediately with **"Server disconnected"**; reproduced directly by spawning the exact generated command from an unrelated directory with a clean environment (no inherited venv, matching how Claude Desktop actually spawns it): `ModuleNotFoundError: No module named 'psycopg2'`. Fixed with `uv run --project <docs-agent dir> mcp_server.py` instead, which resolves against this project's own environment regardless of the caller's working directory. `make mcp-install` automates this registration and rewrites the generated config entry with the `--project` flag and required environment variables automatically.
3. **`add_document()` had no protection against re-ingesting the same file** — asking Claude Desktop to add a document already in the knowledge base silently duplicated its chunks. With a small corpus and a fixed `RETRIEVAL_TOP_K`, duplicate copies of the same chunks crowded out other, genuinely relevant unique chunks from a real query's top-k results — directly degrading answer quality, not just cleanliness. `add_document()` now raises `ValueError` if `VectorStore.has_chunks_from_source()` says the file's already present, with an explicit `force=True` escape hatch for genuinely wanting a duplicate.
4. When forced to answer from the knowledge base alone (via `/my-docs`), the model correctly identified that a "Technology Stack" list was retrieved incompletely — a bullet point split across two adjacent chunks, and the query only surfaced one of them. Root cause, confirmed by inspecting `retrieve_chunks()`'s actual output: it was bug 3 above — duplicate chunks were occupying the other top-k slots that should have gone to the chunk with the rest of the list.
5. Re-adding an already-present document (bug 3's guard, working as designed) surfaced with a **completely blank error message** in Claude Desktop. Cause: `mcp_server.py`'s `add_document` let the plain `ValueError` propagate, and the MCP SDK treats any exception besides its own `ToolError`/`MCPError` as an unexpected crash — deliberately hiding the exception's text from the client. Fixed by catching `ValueError`/`FileNotFoundError` (the specific, "the model could retry with different arguments" cases) and re-raising as `ToolError`, whose message does reach the client.

## 2026-09-18 — Hybrid search: full-text query was silently ANDing every word of the question (`b6b3d34`)

Found while building the retrieval eval script, not by inspection: `search_fulltext()` originally passed the raw question straight into `websearch_to_tsquery('simple', question)`. The `simple` text-search configuration has no stopword list (chosen deliberately, since the corpus mixes Hungarian and English), so every word of the question — including grammar words — became a **mandatory** term (`websearch_to_tsquery` ANDs bare words together). A real chunk almost never contains a question's grammar words verbatim, so keyword search was silently returning **zero results for nearly every natural-language question**, undetected until the eval script's real numbers showed `0 keyword result(s)` on every single run.

Fixed by OR-joining the question's words (`" or ".join(query_text.split())`) before passing them to `websearch_to_tsquery`, so a chunk matching *any* of the question's content words now contributes to RRF fusion. Covered by a unit test (asserts the OR-joined string reaches the query) and a DB test (a real sentence full of grammar words that would have failed pre-fix).

## 2026-09-18 — Chunking: paragraphs spanning a page boundary were silently truncated (`fabbabe`)

Chunking used to run per page (`chunk_pages()`), with no overlap between pages — a paragraph that happened to span a page break was silently split into two truncated, unrelated chunks. `ingest.py` now concatenates the whole document first (`pdf_loader.extract_document_text()`) and chunks that (`chunker.chunk_document()`), so there's no page loop left to truncate anything at a page boundary. `chunk_pages()` itself is unchanged and still used by `eval_cli.py extract`-adjacent tooling and its own tests.

Since a chunk's words can now come from more than one page, `page_number` in its metadata is assigned by majority vote (whichever page contributed the most words) rather than a page range.

## 2026-09-17 — Chunking: `split` shown to catch what `warn` misses (`2404c3e`)

Verified against a real document, with an earlier embedding model whose sequence limit was 128 tokens (not the current default model's 512): with `CHUNK_SIZE=50` words and `WORDS_PER_TOKEN=0.4`, the `warn` heuristic estimated `50 / 0.4 = 125` tokens — just under the 128-token limit, so it **didn't warn at all**. Yet 8 of the 21 actual chunks (38%) really did exceed 128 tokens (up to 198), because real token count varies a lot per chunk's content, not just per configured size. `split` caught and corrected all 8 (21 → 29 chunks), each landing between 53 and 127 tokens — no near-empty stragglers, and afterward zero chunks exceeded the limit.

This is the finding that later motivated making `split` the default (see the 2026-09-26 chunking-defaults entry above).
