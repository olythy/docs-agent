# Engineering Decisions & Bug Log

A dated, reverse-chronological log of what was tried, what broke, and why the current defaults in `README.md` are what they are. `README.md` describes the system as it stands today; this file is the running "why," kept out of the README so reference and history don't keep drifting into one document. Newest entries first. Each entry names the commit(s) it came from.

## 2026-10-03 — `text-embedding-005` is English-only; switched to `text-multilingual-embedding-002` (pending commit, pending re-ingest)

A second opinion (an independent Opus-driven code review of the near-duplicate-boilerplate retrieval problem) raised a possibility that would have reframed the whole investigation: `EMBEDDING_MODEL=text-embedding-005` is Vertex AI's *default* RAG embedding model, adopted for that reason alone -- but Google's own docs state every text embedding model is *evaluated* on English text specifically, with `text-multilingual-embedding-002` named as the model actually recommended for multilingual use. This had gone unchecked through a full day of live measurement on an all-Hungarian legal corpus.

Confirmed live, not just read: re-embedding two already-diagnosed-as-failing golden questions with `text-multilingual-embedding-002` moved their correct document(s) from *below several wrong documents* (0.68-0.72 vs. 0.77-0.79 under `text-embedding-005`) to **rank #1** (single-document question) and **rank #1 and #2** (two-document question) among a 15-17-document random pool. A broader, 6-question systematic sample (2 target documents each, so 12 data points) showed the same model dropping average target rank from ~4.25 to ~3.5 -- a real, consistent improvement, though milder than the two standout cases, and not uniformly positive (one target got worse on one question) -- so the model switch is necessary but was never going to be sufficient on its own for the harder near-duplicate-boilerplate problem.

**Also checked, found fine**: whether `RERANKER_DRIVER=vertex`'s `semantic-ranker-default@latest` had the same English-only issue -- Google's docs didn't state its language support either way, so compared it live, head-to-head, against `JinaRerankerDriver` (explicitly named `jina-reranker-v2-base-multilingual`) on the same Hungarian two-document question. Both independently ranked both correct documents at #0/#1, clearly separated from the rest, agreeing closely on relative scores -- no reranker change needed. (Reciprocal Rank Fusion itself was also considered and ruled out as a place this class of bug could hide: RRF only combines *ranks* from already-independent retrieval signals, with no language/model-dependent step of its own.)

**Fix**: switched `EMBEDDING_MODEL` to `text-multilingual-embedding-002` in `.env`/`.env.example`, documented in `config.py`. Added a new "Model selection" rule to `AGENTS.md`: verify a model's documented language/domain fit against the provider's own current docs before adopting it for any driver, and run a small live A/B check before committing to a switch that requires re-ingestion -- this exact mistake (trusting "it's the default/recommended for RAG" without checking it was evaluated on the project's actual language) is the reason the rule exists.

**Not done yet**: re-ingesting the corpus with the new model (a different vector space, so a document-identifier-header-fix-style targeted re-ingest won't work here -- every already-ingested document needs new embeddings). Bundling this with the other already-deferred ingestion-time changes (decision-date extraction, possibly Hungarian-stemmed full-text search, possibly boilerplate-chunk suppression -- all raised in the same review) into one re-ingestion event is the next planning step, not yet decided.

## 2026-10-03 — Added a Strategy-based GradingStrategy for category-style golden questions; found a much bigger, unrelated bug while validating it (pending commit)

**The methodology problem**: `precedent_seeker`/`synthesizer` questions ask about a *category or pattern* of case (e.g. "which cases involve X type of ruling"), and their own `citation_expectation` in `personas.json` already says "one or more... based on content/legal pattern, not region" -- not a fixed pair. The original grading (`check_retrieval_hit`/`grade_answer`, now `ExactMatchGradingStrategy`) compared against the *one* document a human happened to sample when the question was drafted, scoring a retrieved-and-cited *different*, equally real and on-topic document as "wrong." Confirmed live on `q0026`: 2 of 4 chunks the system actually retrieved (`K_700262_2021_23.docx`, `K_701648_2021_25.docx`) turned out, on reading their real "per tárgya" line, to be genuinely about the exact same subject (kisajátítási ügyben hozott közigazgatási határozat felülvizsgálata) as the golden question's own expected citations -- correct retrieval, scored as a complete miss.

**Fix**: a `GradingStrategy` ABC (`corpus/commands/eval.py`) with two implementations, selected per persona via a new `grading_strategies` list in `personas.json` (a persona can configure more than one at once, e.g. during a transition, and `print_report()` now prints one row per `(persona, strategy)` pair found):
- `ExactMatchGradingStrategy` -- unchanged original behavior, kept for `fact_finder`/`practical_procedural`/`adversarial`, where exactly one answer really is correct.
- `IndependentFactGradingStrategy` -- for `precedent_seeker`/`synthesizer`: extracts whatever citation(s) the *generated answer itself* actually states (via `extract_identifier_tokens`/`search_by_identifier`, the same deterministic mechanism `query.retrieval`'s identifier-rescue already uses, reused here to verify an answer's own claim instead of a question's), verifies it exists, then runs a separate LLM call checking whether that document's real content satisfies the *question's own stated criteria* -- never compared against the golden `citations`/`expected_answer` at all.

Extracted the citation-existence/content-fetch primitives shared with `corpus/commands/generate_questions.py` into `corpus/verification.py` (pure logic only -- each caller keeps its own prompt text, since "verify a drafted question" and "grade a live answer" are different enough jobs that sharing prompt text would blur them).

**Found while validating this live, far more consequential**: the very first test run (`q0026` under the new strategy) returned an answer cut off mid-sentence with zero citations -- `response.candidates[0].finish_reason` was `MAX_TOKENS`, and `usage_metadata` showed `candidates_token_count=39` against `thoughts_token_count=981`. `gemini-2.5-flash` is a "thinking" model: `max_output_tokens` is a *shared* budget across hidden reasoning and the visible answer, and the model spent nearly all of it thinking, leaving almost nothing for the answer itself. This silently truncated answers across **every** persona and **both** grading strategies -- not a grading-methodology problem at all, a generation-pipeline bug that happened to surface while testing the new strategy. Fixed with a new `LLM_THINKING_BUDGET` setting (default `0`, i.e. disabled), passed as `thinking_config=types.ThinkingConfig(thinking_budget=...)` in `GeminiAnswerDriver._generate()` (inherited unchanged by `VertexAnswerDriver`). Confirmed live, post-fix: the same `q0026` query now returns a complete, 2400+ character answer citing four real, correctly on-topic documents, including the two `IndependentFactGradingStrategy` had already flagged as valid alternates.

## 2026-10-03 — Deferred: extract the decision date too, from the document's *end*, not its header (confirmed real, not yet built)

While diagnosing why `precedent_seeker` questions over near-duplicate boilerplate decisions are hard to disambiguate, considered adding the decision's own date (not just the year already embedded in the case number) as a second kind of `document_identifiers` fact -- a genuine, verifiable, document-type-specific distinguishing detail (e.g. "the 2022 kisajátítási ügy" vs. "the 2021 one" at the same court on the same topic) that golden questions could cite, same way they already cite outcomes/sub-topics per the existing multi-document disambiguation guidance in `SKILL.md`.

Checked live on a random sample of 20 ingested documents, in two places: the document's own header/first-chunk area (0/20 had a date there) and the *end* of the document, near the judge's signature (18/20 matched a clean `"<Város>, <YYYY>. <hónap> <nap>."` pattern, e.g. `"Debrecen, 2024. március 26."`, immediately before `"... s. k. bíró"`). The 2 misses genuinely have no date anywhere in their extracted text (just `"Indokolás"` and a bare signature) -- the same kind of real, accepted data gap already documented for case numbers, not a search-logic bug. No sample had a date *without* a preceding city name, but the city should stay an optional prefix in whatever regex eventually implements this, in case a differently-formatted document lacks it.

**Not built now, deliberately**: like the DOCX header/footer fix, this is an *ingestion-time* change (a new extraction step, prepended to every chunk the same way `document_identifiers` already is) -- applying it would mean re-ingesting again. Given the corpus is already mid-re-ingestion after yesterday's header fix, and today's priority shifted to the eval-methodology question below, this is queued as the next ingestion-time change rather than interrupting either.

## 2026-10-02 — pgvector's default `hnsw.ef_search` (40) was silently truncating vector search as the corpus grew (pending commit)

`precedent_seeker`'s eval dropped back to 0/12 after today's growth to 62,243 chunks (up from a few thousand in earlier sessions) -- a much bigger regression than the already-known near-duplicate-boilerplate dilution problem could explain on its own, since even a *single-document* question (`q0030`, no compound-question complexity at all) missed its target entirely. Investigated directly rather than assuming a code regression: `store.search(qvec, top_k=2272, min_score=-1.0)` returned only ~39 rows -- nowhere near the requested `LIMIT`. `SHOW hnsw.ef_search` confirmed pgvector's own default (40): the HNSW index only explores ~40 candidates per query *at all*, regardless of the SQL `LIMIT` requested on top of it -- a ceiling this project's own `RETRIEVAL_TOP_K`/`RETRIEVAL_CANDIDATE_POOL_SIZE` settings sit downstream of and have no way to see past.

**Fix**: new `HNSW_EF_SEARCH` setting (default 400), applied via `SET hnsw.ef_search = ...` on every connection in `db.get_connection()` -- the single canonical place every query already goes through, so no caller needs to remember to set it.

**Important finding while verifying this**: raising `ef_search` alone did *not* rescue `q0030` specifically. Brute-force (index-free) cosine similarity against every one of that document's 15 chunks landed in the 0.68-0.72 range, genuinely lower than several wrong documents' 0.77-0.79 -- confirming this particular miss is the already-documented near-duplicate-boilerplate dilution problem, not an index-recall artifact. The two issues are independent: the `ef_search` default was a real, separate bug (worth fixing regardless, since it silently caps *every* vector query as the corpus scales, for *any* question), but it is not a substitute for solving the harder, structural problem of distinguishing near-identical template documents by embedding similarity alone -- that remains open.

## 2026-10-02 — Fixed the deferred DOCX header/footer gap; targeted re-ingest instead of a full one (pending commit)

Implements the fix deferred earlier today: `_docx_text_and_headers()` (`ingestion/extractors.py`) now also reads `document.sections[0].header`'s paragraphs and prepends that text to `full_text`, with matching `word_section_map`/`word_header_map` entries (empty-string header path, since a running page header isn't a center-aligned body section title). `document.paragraphs` structurally excludes header/footer content in `python-docx`'s API, which is why this was invisible no matter how body text was scanned. Confirmed live on the real failing case (`q0029`'s source document): the real case number (`"4.P.20.434/2019/38*"`) is only in the header, and is now found by `extract_document_identifiers()`; word-array lengths stay in sync (3508/3508/3508 on that document).

**Scope decision**: rather than a full corpus re-ingest, queried `document_chunks` for every currently-ingested document with an empty `document_identifiers` (124 of 2273 ingested so far, ~5.5%) and re-ingested (`add_document(..., force=True)`) only that subset. Safe to do narrowly: for every *unaffected* document, the fix is a no-op (no header text to find, or the identifier was already found in the body either way), so old-code and new-code ingestion produce identical output for them -- there's no "mixed schema" risk to worry about, unlike changes that affect every document's chunking uniformly. The concurrent bulk `add_directory()` run (still working through the remaining ~8,200 documents) was stopped before this fix landed and will be resumed with the fix already in place, so no further documents should need this same retroactive pass.

## 2026-10-02 — Deferred: read Word header/footer text during DOCX extraction (confirmed real, not yet fixed)

Investigated the already-known gap (a document's case number sometimes isn't present in its extracted text at all -- see the 2026-10-02 header-enrichment entry below) on a concrete failing case, `q0029`: `Balassagyarmati_Jarasbirosag__P_20434_2019_38.docx`. Confirmed directly with `python-docx` that the real case number (`"4.P.20.434/2019/38*"`, near-identical to the citation that failed verification) lives in the document's **header** (`document.sections[0].header`), not its body -- `DocxExtractor`/`_docx_text_and_headers()` only ever iterates `document.paragraphs`, which structurally excludes header/footer content in `python-docx`'s API; there was never a chance of finding it there.

This also explains the specific *way* `q0029` failed: tier-2 verification correctly found a *different*, real case number in the body text (a related/underlying proceeding this judgment reviews) and flagged a mismatch against the cited number -- a reasonable conclusion given what it could see, just blind to the header where the actually-correct number was.

**Not fixed now, deliberately**: the fix isn't a quick read-and-append -- `_docx_text_and_headers()` would need to prepend header words to `full_text` *and* extend `word_section_map`/`word_header_map` with matching entries for those words, keeping every array's index alignment intact (the same constraint that already shapes the rest of that function). Changing extraction logic while a multi-hour bulk ingest is running would also split the corpus into "ingested before the fix" and "ingested after," another reason to treat this as its own, separate piece of work rather than a mid-flight patch.

## 2026-10-02 — `generate-questions` must not cite a document it couldn't verify an identifier for (pending commit)

Second finding from the same `needs_review` batch as the entry above: `q0035` (`synthesizer`) correctly left a citation's `court`/`case_number` blank rather than guessing -- the right call per the existing instruction to say so in `notes` instead of guessing -- but still went ahead and cited that document as one of its two sources anyway. The blank fields then failed Part 2's verbatim check, a foreseeable outcome at drafting time: leaving fields blank is only safe as a *reason not to use* a sample, not as a way to still use one in `citations`.

**Fix**: added a `SKILL.md` Part 1 instruction: if a given sample doesn't yield a verifiable court/case number, don't cite it at all -- draft the question around whichever sample(s) do verify, even if that means fewer citations than samples given, rather than forcing a multi-document question out of material that doesn't support it. No code change needed: `corpus/commands/generate_questions.py` never required `len(citations) == len(samples)` in the first place, only that `citations` be non-empty.

## 2026-10-02 — `generate-questions` was "correcting" `source_file`'s spelling, breaking the exact-match lookup it depends on (pending commit)

Resumed golden-set generation (`precedent_seeker`/`synthesizer`, 5 each) now that the local DB is growing again post-ingest-restart. 3 of the 10 drafted questions came back `needs_review`. Two of the three (`q0032`, `q0034`) failed on the same new root cause: `citations[].source_file` read `Budapest_Kornyeki_Torvenyszék__...` (accented "é") while the real, ingested filename is `Budapest_Kornyeki_Torvenyszek__...` (plain ASCII, like every filename in this corpus) -- `verify_citation_exists()`'s exact-string DB lookup correctly failed to find it.

Unlike the already-documented `court`/`case_number` hint-copying bug (where the model echoed an *unreliable* filename-derived guess verbatim instead of reading the real value from content), this was the opposite mistake on the *one* field that actually is authoritative: the model "corrected" a technically-misspelled-looking filename back to proper Hungarian orthography, not realizing `source_file` must be copied character-for-character, not treated as prose. (The remaining `needs_review` case, `q0029`, is the already-known, separate issue of a document whose real case number isn't present in its extracted text at all -- not a new bug.)

**Fix**: added an explicit `SKILL.md` Part 1 instruction distinguishing `source_file` (authoritative, exact, never "improved") from `court`/`case_number` (unreliable hints, read the real value from content instead). Confirmed live: regenerated 2 more `synthesizer` questions post-fix, both `verified`, all 4 of their citations' `source_file` values exactly unaccented.

## 2026-10-02 — All three Vertex drivers now invalidate the cached gcloud token on a 401 (pending commit)

A real, several-hours-long bulk ingest (`EMBEDDING_DRIVER=vertex`) crashed on `401 Unauthorized` -- `drivers/gcloud_auth.py`'s cached token assumes a fixed ~1-hour lifetime and only refetches once that assumption's clock runs out, but a token can evidently stop working before that. The 401 wasn't retried at all: `VertexEmbeddingDriver._embed_one_batch()` only ever classified 429/5xx as a retryable `TransientAPIError`; everything else fell through to `response.raise_for_status()`, an unretried `HTTPStatusError` that propagated straight up and ended the whole `add_directory()` run.

Blindly retrying a 401 wouldn't have been enough on its own, either: `retry_on_transient_error`'s decorator just re-runs the same function from the top, which would call `get_access_token()` again -- and get back the *same* still-cached token, failing identically on every attempt until retries exhausted.

**Fix**: added `drivers.gcloud_auth.invalidate()` (clears the cached token so the next `get_access_token()` call is forced to refetch). All three Vertex drivers now call it specifically on a 401, immediately before raising `TransientAPIError` to trigger the existing retry decorator -- `VertexEmbeddingDriver`/`VertexRankerDriver` (raw `httpx` status code) and `VertexAnswerDriver` (inherits `GeminiAnswerDriver._generate()` unchanged, where the 401 instead arrives as `google.genai.errors.APIError(code=401)` via the SDK). The `_generate()` case is a no-op for `GeminiAnswerDriver` itself (AI Studio mode never touches `gcloud_auth`), left in the shared method anyway rather than duplicating the whole method just to special-case Vertex.

## 2026-10-02 — Added VertexAnswerDriver, completing the embedding/reranker/LLM move off free-tier caps (pending commit)

Same question raised for the LLM as had already been answered for embedding and reranking: AI Studio's free-tier Gemini quota (`LLM_DRIVER=gemini`) was also a throughput ceiling, so could Vertex AI solve it the same way it already had for the other two drivers? Checked before building anything: the `google-genai` SDK's `vertexai=True` mode turned out to accept a manually-constructed `google.auth.credentials.Credentials` object wrapping `drivers.gcloud_auth.get_access_token()` -- confirmed live with one real call, then a 10-request burst, both clean -- so the same "authenticate via the already-logged-in `gcloud` CLI session" approach used for the embedding/reranker drivers works here too, without needing a separate `gcloud auth application-default login`.

This made `VertexAnswerDriver` a very small addition: it subclasses `GeminiAnswerDriver` and overrides only `_get_client()` (constructing with `vertexai=True, project=, location=, credentials=` instead of `api_key=`) -- every other method (`answer()`, `run_tool_calling_turn()`, `_generate()`'s retry/throttling/error handling) is identical between AI Studio and Vertex AI in the `google-genai` SDK; the backend is purely a client-construction detail, confirmed by reading through `_generate()` and finding nothing AI-Studio-specific in it.

Added `get_credentials()` to `drivers/gcloud_auth.py` alongside the existing `get_access_token()`: a `Credentials` subclass whose `valid` property always returns `False`, forcing any caller to call `refresh()` before every use -- `refresh()` just delegates to `get_access_token()`'s own freshness check. Without this override, the base class's default `valid` becomes `True` forever once a token is set (since `expiry` is never populated here), and nothing would ever pick up a refreshed token again after the first call.

With this, all three of the project's AI-dependent concerns (embedding, reranking, answer generation) now have a Vertex AI option available, each one added only after its free-tier counterpart (Jina or AI Studio) hit a real, live quota wall during actual use -- not pre-emptively.

## 2026-10-02 — Added VertexRankerDriver after Jina's cap hit the reranker too; extracted shared gcloud_auth (pending commit)

A real `corpus/cli.py eval` run hit the exact same Jina `RATE_TOKEN_LIMIT_EXCEEDED` (100K tokens/minute) that had already interrupted bulk ingest -- this time from `JinaRerankerDriver`, which had no throttling at all (unlike `JinaEmbeddingDriver`, which at least has `EMBEDDING_REQUEST_DELAY_SECONDS`). Since `VertexEmbeddingDriver` had already proven that this GCP project's default quota tolerates rapid, undelayed requests, the natural fix was the same pattern, not a Jina-side throttle: added `VertexRankerDriver`, calling Google Cloud's standalone Discovery Engine Ranking API (`rankingConfigs/default_ranking_config:rank`) directly -- confirmed via docs that this and the text embedding API are both usable independently of the full managed Vertex AI RAG Engine corpus/vector-store package, so neither driver requires buying into that. Confirmed live before writing code: 15 rapid, undelayed rank requests against this project's default quota all succeeded, and the live-scored relevance (0.76 relevant vs. 0.02 irrelevant) matched the earlier `VertexEmbeddingDriver` similarity check's directional correctness.

**Refactor while adding it**: extracted the access-token caching logic (previously inline in `VertexEmbeddingDriver`, shelling out to `gcloud auth print-access-token`) into a new shared module, `drivers/gcloud_auth.py`, used by both Vertex drivers. Caching it at module level rather than per-driver-instance means two separate Vertex drivers in the same process (embedding + reranking) share one token and one `gcloud` subprocess call, not one each. This introduced a real test-isolation gap: the module-level cache persists across test functions within a session, so a test that warms it can make a *later*, unrelated test's `subprocess.run` mock never actually get called, silently breaking that test's own assertions -- fixed by resetting the cache in the existing `clear_driver_caches` autouse fixture (`tests/conftest.py`), alongside the driver-factory `lru_cache` resets already there for the same underlying reason.

## 2026-10-02 — VertexEmbeddingDriver needed token-count batching too, and WORDS_PER_TOKEN was the wrong ratio to reuse (pending commit)

First real bulk-ingest use of the freshly-added `VertexEmbeddingDriver` hit `400 INVALID_ARGUMENT: input token count is 61864 but the model supports up to 20000` on a 44-chunk document -- the driver's `_MAX_BATCH_SIZE=250` only capped instance count, not the API's separate, stricter total-input-token cap, which a handful of long chunks can exceed well before 250 instances do.

First fix attempt reused the project's general `settings.WORDS_PER_TOKEN` (0.75, i.e. ~1.33 tokens/word) to estimate a safe batching threshold -- still failed on a *second*, independent real-content test (20 real 251-word chunks, `400` again, actual count 22,276 tokens for 4,484 words). Confirmed live: this API's real tokenizer produces **~5 tokens per word** on Hungarian legal text, not ~1.33 -- `WORDS_PER_TOKEN` is calibrated for the *local sentence-transformer model's* tokenizer (an English-average assumption, per `ingestion/chunker.py`'s own docstring) and is simply the wrong ratio for a different model's tokenizer, not a matter of needing more safety margin on the same number.

**Fix**: `VertexEmbeddingDriver` now batches by both instance count (`_MAX_BATCH_SIZE=250`) and an estimated token count (`_MAX_TOKENS_PER_BATCH=15000`, under the API's real 20,000 cap for margin), using its own empirically-measured `_ESTIMATED_TOKENS_PER_WORD=5.5` constant instead of the shared `WORDS_PER_TOKEN` setting. Confirmed live, post-fix, that both previously-failing real cases (the 44-chunk document, the 20-real-chunk batch) now succeed. Considered using the API's own `CountTokens` endpoint for an exact count instead of estimating -- rejected for now, since it would double the request count for a number this estimate already confirmed empirically close to correct.

## 2026-10-02 — Added VertexEmbeddingDriver after Jina's token-per-minute cap kept interrupting bulk ingest (pending commit)

Even with `EMBEDDING_REQUEST_DELAY_SECONDS=1.5` throttling (see the entry below), a real bulk `add_directory()` ingest over the full ~10,491-document corpus kept occasionally hitting Jina's 100K-tokens/minute cap, because a flat per-document delay can't account for how much chunk count/token load varies document to document -- a burst of several large documents in a row can still exceed the budget even when the average document wouldn't. This also meant the ingest and any concurrent eval/retrieval testing competed for the same shared Jina quota, making it hard to test anything while a bulk ingest was running.

**Considered and rejected**: raising the delay further (e.g. to 2.5s) -- would reduce 429s but slow down every small document too, wasteful for the common case to guard against the uncommon one (a token-count-aware adaptive delay would be the "right" fix, but added complexity not justified yet).

**Fix**: added `VertexEmbeddingDriver` (Google Cloud's Vertex AI text embedding API) as another `EMBEDDING_DRIVER` option, billed against GCP credit instead of sharing Jina's free-tier cap. Confirmed live before writing any code: 20 rapid, undelayed requests against this project's default Vertex AI quota all succeeded (`HTTP 200`), vs. Jina's cap triggering within a single small document's worth of calls. Also confirmed `outputDimensionality=384` truncation works (same truncation pattern as every other remote driver) and that relative similarity scoring is sane on real Hungarian legal text (0.78 relevant vs. 0.59 irrelevant cosine similarity).

Authenticates differently from every other driver here: Vertex AI uses OAuth access tokens, not a static API key, so there's no `VERTEX_API_KEY` setting -- `VertexEmbeddingDriver` shells out to the already-authenticated `gcloud auth print-access-token` and caches the token in memory (refreshed 5 minutes before its ~1-hour expiry) rather than requiring a separate Application Default Credentials setup, which would need its own interactive browser login.

**Not yet decided**: whether to actually resume the paused bulk ingest with `EMBEDDING_DRIVER=vertex` instead of `jina` -- both now exist as real, working options.

## 2026-10-02 — JinaEmbeddingDriver needed EMBEDDING_REQUEST_DELAY_SECONDS throttling too (pending commit)

First real bulk ingest with `EMBEDDING_DRIVER=jina` (a fresh re-ingest, now with the `document_identifiers` header-enrichment fix) hit Jina's token-per-minute limit almost immediately: `429 RATE_TOKEN_LIMIT_EXCEEDED, "109,535/100,000 tokens per minute"`. The 3-attempt retry (`retry_on_transient_error`, 2s/4s backoff, ~14s total) correctly caught and retried each 429, but that's nowhere near enough time for a per-minute token bucket to clear, and a plain per-document `add_directory()` loop keeps firing new embedding calls continuously -- the cap is cumulative across many small calls within the same minute, not about any single call's batch size (each document here was only 5 chunks).

**Fix**: `JinaEmbeddingDriver._embed_one_batch()` now sleeps `EMBEDDING_REQUEST_DELAY_SECONDS` before every attempt, same mechanism `GeminiEmbeddingDriver` already had for exactly this kind of free-tier rate limit -- it had simply been omitted when `JinaEmbeddingDriver` was first written. Set to `1.5` in `.env` (was `5.0`, left over from the unrelated `LLM_DRIVER=gemini` config): at ~7.65 chunks/document and ~200-300 tokens/chunk average for this corpus, 1.5s/document keeps throughput around 60-90K tokens/min, under the 100K cap with margin, without throttling as conservatively as the inherited `5.0` would have.

## 2026-10-02 — Added Jina AI embedding/reranker drivers after a GCP GPU infra attempt hit a quota wall (pending commit)

Live profiling (see entries below) identified two real, CPU-bound costs: ingestion-time embedding (~0.28s/chunk, ~90%+ of per-document ingest time on the local model) and query-time reranking (~6s/question, steady-state on the local cross-encoder). Both seemed like a good fit for a self-hosted GPU inference server (HuggingFace Text Embeddings Inference, serving the *same* models to avoid a vector-space-incompatible re-ingestion).

**Attempted and abandoned**: set up `gcloud` for project `agents-dev-510410`. Compute Engine GPUs were first blocked by the billing account still being on the free trial (GPUs are flatly disallowed there); upgrading to paid billing cleared that, but every subsequent attempt (Compute Engine VM with T4 or L4, in `us-central1` and three `europe-west*` regions; Cloud Run with GPU, zonal-redundant and non-redundant) hit a project-wide `compute.googleapis.com/gpus_all_regions` quota of **0** — a separate, overriding cap that makes the individual per-region/per-type quotas (which did show 1 T4 + 1 L4 available) meaningless on their own. Confirmed via `gcloud alpha services quota update` that self-service increase is hard-capped at 0 for this quota; submitted a Console quota-increase request instead, and Google Cloud Support's reply: *"we are unable to grant you additional quota at this time... please wait 48h."* See the dedicated `project_gcp_gpu_infra` memory for the full timeline — not retrying before 2026-10-04.

**Fix, no infra required**: Jina AI's hosted Embeddings/Reranker APIs (`https://api.jina.ai/v1/embeddings`, `/v1/rerank`) solve the same two bottlenecks with a plain HTTPS call, no GPU/VM/quota anywhere. Simpler and more robust to just always prepend unconditionally.

## 2026-09-30 — Deferred: bake each document's identifier into every chunk's header, not just chunk 0

While discussing the identifier-rescue fixes above, a real gap surfaced that today's fixes don't address: a document's case number typically only appears once, near the top (`chunk_index=0`) — `search_by_identifier()` can only find *that* chunk via an exact match, not a different chunk deeper in the same document that might hold the actually-relevant content (e.g. the court's reasoning, several chunks in). Today's `retrieval_hit_rate` metric checks at the *document* level (`source_file` presence), so this gap could be silently masked there even after the identifier-rescue fixes.

The fix would mirror the header-enrichment mechanism `ingestion/chunker.py` already uses for Markdown/DOCX section breadcrumbs (`header_path`): extract each document's identifier once during ingestion and prepend it to every one of that document's chunks, not just the first, so an identifier-based query-time lookup can find whichever chunk actually has the relevant content, not just the header chunk.

**Deliberately not built now**: unlike today's other fixes (all query-time, applied against the already-ingested corpus), this needs an *ingestion*-time change — every already-ingested document (1000+ and growing, still mid-ingestion as of this session) would need to be re-chunked and re-embedded to pick up the new header. Worth doing, but as a deliberate, separate decision once the current ingestion run finishes, not a mid-flight interruption of it.

Immediate follow-up to the identifier-rescue fix below, found by re-running the golden-set eval after marking `q0011`/`q0012` reviewed: `q0002` (`practical_procedural`) still scored a retrieval MISS despite citing a case number that `extract_identifier_tokens()`/`search_by_identifier()` correctly found. Investigated live by reproducing `select_chunks()`'s exact pipeline step by step: the rescued chunk *was* in the candidate pool, *did* pass the cross-encoder's `RERANKER_MIN_SCORE` threshold (score 3.63 vs. the -2.0 floor) — but ranked **14th** overall, well past `top_k`'s default cutoff, because 13 other chunks read as more generically on-topic to the cross-encoder (which has no notion that a chunk is definitionally correct because its identifier matches).

Considered and rejected raising `top_k` instead: confirmed live that the rescued chunk's actual rank (14th) would need `top_k=14+` to survive by chance alone, for this one question — inflating every query's LLM context size/cost, and still not a guarantee for a different question where the rescued chunk might rank 30th or lower.

**Fix**: added `_apply_top_k_with_guarantees()` — partitions the reranked, score-filtered chunks into "identifier-guaranteed" (by id, tracked from `search_by_identifier()`'s own results, not just the ones newly merged into the fused pool) and "everything else," keeping all guaranteed chunks plus the highest-scoring remainder up to `top_k` total. Confirms the design principle from the same discussion that produced the original identifier-rescue: merging into the candidate pool and passing the relevance floor isn't sufficient on its own — the final count-based cutoff needed its own explicit guarantee too, since it's a different kind of cut (how many to show) than the relevance floor (is this relevant at all), which the guarantee deliberately still respects.

**Scope note, discussed explicitly and confirmed still correct**: this mechanism (`extract_identifier_tokens`/`search_by_identifier`/the guarantee) remains fully document-type-agnostic by construction — nothing in it references court decisions, case numbers, or legal terminology. `_is_inflected_number()` is the one narrow exception, and it's a Hungarian-*language* quirk (numbers with attached grammatical suffixes like "2020-as"), not a document-*type* specialization. Explicitly deferred: generalizing to other "exact match matters" token classes (e.g. short technical terms like "C++" that a semantic/full-text search would also mangle) — a real, plausible future need, but not built now without a real corpus to validate against; the current plain-function design (not a formal Strategy/plugin registry) already composes cheaply enough that adding a second extractor later won't require a rewrite.

## 2026-09-30 — First golden-set eval run found two real bugs: a retrieval blind spot and a generate-questions citation bug (pending commit)

First live run of `corpus/cli.py eval` against the seed golden set immediately did what it was built for: surfaced two real, distinct bugs, not just a "score." One in the RAG pipeline itself, one in the golden-set generation tooling.

**Bug 1 (real, in `query/retrieval.py`): exact identifiers lose to common words in hybrid search's ranking.** `fact_finder` question q0001 asked about a specific case (`4.P.20.409/2023/4`) and scored a retrieval MISS. Investigated live, not assumed: confirmed the correct document's raw cosine similarity (0.8847) sat *below* 10+ other documents (0.8997–0.9053) sharing near-identical legal boilerplate ("a bíróság a felperesek keresetét elutasítja") — vector search alone can't distinguish this specific ruling from dozens of structurally similar ones. Checked `search_fulltext()` too, expecting it to compensate: also missed the document entirely. Root cause, confirmed via `to_tsvector`/`websearch_to_tsquery` directly: the case number *does* match as an exact phrase (`'4' <-> 'p.20.409/2023/4'`), but `prepare_fulltext_query()` OR-joins it together with all the question's other (extremely common) words, and `ts_rank` scores by aggregate frequency/coverage — the rare, precise match gets outscored by documents matching the common words more thoroughly.

Also confirmed live via `HybridRetrievalStrategy.select_chunks()`'s own code (not assumed): vector search and full-text search are two fully independent queries over the whole table, merged only via RRF *after* each already ran — RRF can't rescue a candidate neither independent search found in the first place.

**Fix**: added `extract_identifier_tokens()`/`VectorStore.search_by_identifier()` (`store.py`) — a third, independent lookup for code-like identifier tokens (case numbers, invoice numbers, contract references — deliberately document-type-agnostic, not court-decision-specific, since the same gap would affect a contract or invoice corpus too), merged directly ahead of the RRF-fused list in `HybridRetrievalStrategy`, bypassing `ts_rank` scoring entirely for these tokens rather than trying to out-weight it. A token counts as identifier-like if it mixes letters+digits, contains a separator (`.`/`/`/`-`), or is a pure number 5+ digits long (long enough not to just be a year) — refined once more after a real false positive: "2020-as"/"2022-es" (Hungarian "of 2020"/"of 2022") matched the digit+separator rule and, being extremely common, flooded `search_by_identifier`'s result limit ahead of the real case numbers in the same question. Added `_is_inflected_number()` to exclude this specific shape (bare digits + hyphen + short lowercase suffix) rather than trying to solve Hungarian morphology generally. Verified live: q0001 now hits.

**Bug 2 (in the golden-set tooling, not the RAG pipeline): `generate-questions` sometimes cites the wrong case number.** q0006/q0007 (the `precedent_seeker`/`synthesizer` multi-document personas) both scored a full retrieval MISS on *both* citations. Investigated live: q0007's cited `G.40110.2020.29` doesn't exist anywhere — the real case number, found by searching the actual document content directly, is `15.G.40.110/2020/5` (different formatting *and* a different trailing number). q0006's cited numbers didn't appear in either target document at all, in any form.

Root cause: `sample_chunks_for_persona()` hands the drafting LLM a `case_number` field reconstructed from the filename (`_case_number_from_filename()`, already documented as "best-effort only, not authoritative" — it can't know about prefixes or exact in-document punctuation) as prompt *context*. The model then copied that unreliable hint straight into its own citation instead of reading the real case number out of the given `content`. Not hallucination in the usual sense — it faithfully used what we ourselves handed it. The tier-2 verification step didn't catch it because it only asked "does the content substantively support the answer" (a semantic check), not "does the exact cited case number appear in the content" (a literal-presence check) — the answer's substance was fine, only the citation was wrong.

**Fix**: `SKILL.md` now explicitly tells the drafting model the given `case_number` is an unreliable hint and to find the real one written in the content before citing it, and Part 2's verification explicitly requires the cited case number to appear verbatim (or near-verbatim) in the content as its own sub-check, independent of and prerequisite to the substantive-support check. q0006/q0007 deleted and regenerated as q0011/q0012 through the fixed pipeline; spot-checked live (not just trusting the self-reported verification) that both new citations' case numbers appear verbatim in their real source documents.

Instead, built a **hybrid Skill** (`skills/generate-golden-questions/`, the first skill in this project — `skills/README.md` had already anticipated this exact purpose), following the same one-prompt-two-callers pattern discussed for the corpus downloader: `SKILL.md`'s instructions either drive Claude Code directly (reads real chunk content, drafts the question with its own judgment — the higher-quality path) or get sent as a prompt to `get_answer_driver()` for unattended CLI runs (`cli.py`) — noisier, since there's no judgment call to skip a bad sample, which is exactly why every draft, from either path, goes through the same verification gate before being trusted.

**Two-tier verification, not manual review of all 1000**: (1) a deterministic check that each cited `(court, case_number, source_file)` actually matches a real ingested document; (2) a **separate** `get_answer_driver()` call (never the same call that drafted the question — it must not grade its own work) judging whether the cited document's real, full content actually supports the drafted `expected_answer` (`SUPPORTED`/`NOT_SUPPORTED`/`UNCLEAR`, substance not string-match, so paraphrasing doesn't get penalized). Anything short of a clean `SUPPORTED` gets `verification_status: "needs_review"` instead of being silently trusted — this is what makes the CLI's unattended, noisier drafting path safe to use at all: the safety comes from the gate, not from trusting either drafting path unconditionally.

Verified live, end-to-end, immediately after building it: `cli.py fact_finder 1` and `cli.py adversarial 1` each drafted a real question against the live Supabase corpus and the currently-configured `LLM_DRIVER=gemini`, passed both verification tiers, and were appended to `questions.json` with real, correct-looking Hungarian legal content — not just unit-tested in isolation. No automated tests were added for `cli.py` itself, matching the precedent already set for `corpus/download_court_decisions.py` (the other hybrid script/skill artifact in this project): both are one-off tooling around the core pipeline, not part of it, verified live rather than via pytest.

## 2026-09-30 — Fixed Gemini drivers not retrying network errors (pending commit)

Found live, mid-way through the first full 10,491-document corpus ingestion: a transient WiFi drop (`httpx.ConnectError: [Errno 65] No route to host`) crashed the entire `add_directory()` run instead of failing just the one in-flight batch. Root cause: `GeminiEmbeddingDriver._embed_one_batch()`/`GeminiAnswerDriver._generate()` only caught `google.genai.errors.APIError` (Gemini's own API-level error type, e.g. a 429/5xx *response*) — but `google-genai` uses `httpx` internally, and a connection-level failure (DNS error, no route, timeout) raises `httpx.TransportError`, a completely unrelated exception hierarchy that was never retried at all and isn't an `OSError` subclass either, so `ingestion.ingest.add_directory()`'s per-file `except (..., OSError)` didn't catch it as a per-file failure — it propagated all the way up and killed the whole run.

## 2026-09-29 — Deduplicated retry-with-backoff logic into `retry.py` via `tenacity` (`83e260b`)

By the time the native Gemini driver (below) was added, the same hand-rolled retry loop (manual `for attempt in range(...)`, `backoff_seconds *= 2`, per-call-site `time.sleep`) was duplicated three times: `OpenRouterEmbeddingDriver._embed_one_batch`, `GeminiEmbeddingDriver._embed_one_batch`, and `corpus/download_court_decisions.py`'s `request_with_retries()`. Flagged as not a good path to keep extending — a fourth caller would have meant a fourth copy.

Added `tenacity` (`uv add tenacity`) rather than hand-rolling a shared decorator: it's a well-established, actively maintained retry library, and none of these three call sites needed anything tenacity doesn't already do off the shelf. Considered `asyncio`-based retry/backoff instead, but rejected — nothing in this codebase is `async` (`grep -rn "async def\|asyncio"` across the project returns nothing), so that would have meant asyncifying every caller up the stack (drivers → ingestion → CLI) for no benefit over a synchronous decorator.

New `retry.py` (top-level, alongside `db.py`/`models.py`/`logger.py`) exports `TransientAPIError` (raised by a call site to mark a failure as retryable) and `retry_on_transient_error()` (a `tenacity` decorator factory: exponential backoff doubling from 2s, `reraise=True` so the original `TransientAPIError` propagates after the last attempt rather than a wrapped `RetryError`). `TransientAPIError` deliberately subclasses `OSError` — `ingestion/ingest.py`'s per-file `except (ValueError, FileNotFoundError, RuntimeError, OSError)` handling already existed before this change and needed to keep catching a retry-exhausted embedding failure without knowing about the new type; the driver previously raised `requests.RequestException`, itself an `OSError` subclass, so this preserves that behavior rather than silently introducing an uncaught-exception regression.

All three call sites were rewritten to raise `TransientAPIError` for a retryable condition (network error, 429, 5xx) and let any other exception propagate as-is (tenacity's `retry_if_exception_type(TransientAPIError)` only intercepts that one type) — `corpus/download_court_decisions.py`'s `request_with_retries()` keeps its existing external contract (returns `None` after exhausting retries, rather than raising) by applying the decorator to a small inner function and catching `TransientAPIError` at the outer function's boundary, since its `max_retries` is a CLI-configurable value rather than a fixed constant tenacity's decorator syntax can take at class-definition time.

## 2026-09-29 — Switched to `EMBEDDING_DRIVER=openrouter`; made `RERANKER_DRIVER=cross_encoder` the default (`ca9e225`)

Ingesting the real-estate-law corpus with the local embedding driver measured ~17.8s/document (10 real documents, 177.76s total) — projected to **~2 days** of continuous CPU-bound embedding for the full ~10,000-document corpus. Looked for a faster alternative before committing to that.

**`EMBEDDING_DRIVER=openrouter` was added** rather than a native Gemini SDK integration, after discovering (live, via `GET /api/v1/embeddings/models`) that OpenRouter already exposes `google/gemini-embedding-001` — reusable with the *same* OpenRouter account/key this project's `LLM_DRIVER=openrouter` already uses, no new provider account needed. Verified against the real endpoint, not assumed:
- Native output is 3072d, but OpenRouter's `dimensions` request parameter truncates it — confirmed working down to 384, this project's existing `document_chunks` column width, so switching needed **no schema migration** (helped by the table having just been flushed for this restart anyway).
- Real cost: `1.65e-06` per 11-token call ≈ **$0.15/1M tokens** ≈ **~$5 for the full corpus** — cheap enough not to be a real constraint.
- Real speed on 10 real documents (word chunking, see below): **55.7s total ≈ 5.6s/doc**, ~3.2× faster than local, projecting to **~15-16 hours** for the full corpus instead of ~2 days.

**Two real bugs found via the same live re-ingestion test, not by inspection:**
1. The API hard-rejects a batch over 250 items: `HTTP 400`, *"batchSize value of 300 but the supported range is from 1 (inclusive) to 251 (exclusive)"*. `OpenRouterEmbeddingDriver.embed_batch()` now splits into sub-batches of at most 250 automatically. Without this, any document producing >250 chunks in one `embed_documents()` call failed outright (3 of the first 10 real documents did).
2. This driver has no real tokenizer (`count_tokens()`/`max_sequence_length()` stay `None`, same as `openai`), and `.env` still had `CHUNKING_STRATEGY=langchain` from earlier local-driver tuning. Without a real tokenizer, `langchain` silently measures `CHUNK_SIZE` in raw *characters*, not words — one real document went from an expected ~15 chunks to **407**. Fixed by setting `CHUNKING_STRATEGY=word` for this driver, which needs no token counting at all.

**A more consequential finding, discovered while sanity-checking the relevance gate against the new model**: a real, obviously relevant Hungarian query scored **0.73–0.76** raw cosine similarity against real ingested content, which sounds fine against `RETRIEVAL_MIN_SCORE=0.25` — until a deliberately *irrelevant* Hungarian query (about frying chicken) also scored **0.54–0.55**, comfortably above the same 0.25 threshold. The `_passes_relevance_gate()` check (`query/retrieval.py`) is vector-only by design (see the README's "What happens when there's no reliable source" section) — with this embedding model, that gate alone can no longer reliably distinguish relevant from irrelevant queries. The threshold was tuned for the local e5 model's similarity scale; nothing guarantees it transfers to a different model's scale, and this is the first time this project actually swapped `EMBEDDING_DRIVER` on a populated index to find out.

**Decided against raising `RETRIEVAL_MIN_SCORE` to compensate.** The vector gate is a cheap, coarse, single-number threshold — tightening it risks rejecting genuinely relevant chunks that simply don't score well under raw cosine similarity (different phrasing, topically-adjacent-but-correct content), trading false negatives for false positives on too little data (two anecdotal queries) to calibrate responsibly. Real recalibration is deferred to the golden-set/eval work already planned, where there'll be enough labeled examples to tune against instead of guessing.

**Instead, re-tested with `RERANKER_DRIVER=cross_encoder` enabled** (previously not the default — see the 2026-09-26 "Cross-encoder logit calibration" entry). The reranker correctly rejected the irrelevant chicken-frying query (all candidates scored below `RERANKER_MIN_SCORE=-2.0`, correctly returning no results) while keeping the relevant query's chunks (logits 3.6–4.2). This works because the cross-encoder scores `(question, chunk)` *jointly*, not via embedding distance — its relevance judgment isn't tied to any particular embedding model's similarity scale the way the vector gate's threshold is.

**This made `RERANKER_DRIVER=cross_encoder` the new default** (`config.py`, `.env.example`), reversing the original `none` default from the 2026-09-26 entry. That original reasoning ("hybrid fusion is already a reasonable ranking on its own, reranking is optional") held for a single, fixed local embedding model — it doesn't hold once the embedding driver is something users are expected to actually swap, since nothing else in the pipeline then reliably catches an irrelevant query. `none` remains a real, selectable option for comparison/eval (`make eval` vs. the old bare-RRF baseline), just no longer the production default.

## 2026-09-29 — `RtfExtractor`: plain text only, header detection deferred; a real striprtf whitespace quirk (`0f00f1d`)

Second extractor for the real-estate-law corpus, after `DocxExtractor`. Unlike DOCX, RTF has no equally cheap way to get both clean text *and* paragraph-level formatting (alignment) in one library call: `striprtf` (the standard choice for RTF-to-text) discards all formatting, so replicating DOCX's centered-paragraph header signal would require a hand-rolled RTF parser reading `\qc`/`\pard` control words directly. Deferred deliberately rather than built speculatively — as of this decision, 0 of 5743 downloaded corpus documents are RTF, all are DOCX. `RtfExtractor` therefore matches `PDFExtractor`'s level of detail (plain text, no `header_path`), not `DocxExtractor`'s.

**A real library quirk, found via a real (unmocked) test, not assumed**: `striprtf` sometimes swallows the whitespace immediately following a hex-escaped character (`\'e9`), merging it with the next word (`t\'e9 l` → `"té l"`, not `"t é l"`). This only matters for letter-spaced text — which happens to be exactly the convention real corpus documents use for centered section titles ("í t é l e t e t :", see the `DocxExtractor` entry above) — but since `RtfExtractor` doesn't do header detection at all yet, it's a cosmetic spacing slip in body text today, not something anything currently depends on. Documented in the extractor's own docstring and a dedicated regression test, in case it matters once header detection is eventually added for RTF.

Also resolved along the way: RTF files declare their own character encoding via a `\ansicpg<N>` control word in the header — the raw file bytes are decoded as latin-1 first (a 1:1 byte-to-codepoint mapping that never raises, since RTF's control words are pure ASCII and non-ASCII characters are hex-escaped rather than embedded as raw high bytes), then `striprtf` interprets the hex escapes using whichever codec `\ansicpg` declares (defaulting to `cp1250` — Central European — since this corpus is Hungarian, for the rare case it's missing).

## 2026-09-29 — `DocxExtractor`: alignment, not heading styles, is the section-title signal (`977bb00`)

Building the ingestion side for the real-estate-law corpus (`corpus/download_court_decisions.py`), starting with `.docx` since 5555/5555 downloaded so far are DOCX, none RTF. The obvious first guess — use Word's "Heading 1"/"Heading 2" paragraph styles, mirroring how `MarkdownExtractor` uses `#`/`##` — turned out to be wrong: inspecting several real corpus documents' raw XML during the earlier corpus-download work already showed no `w:pStyle` references at all in the document body, just a template's unused style *definitions*. Every paragraph is styled "Normal".

What the documents actually use for section titles ("ítélete", "Indokolás", "A Kúria mint felülvizsgálati bíróság") is **centered paragraph alignment** — confirmed empirically across 5 real documents (`python-docx`, checking `paragraph.alignment == WD_ALIGN_PARAGRAPH.CENTER`): centered paragraphs are rare (2-4 out of 100-400 per document) and were a section title in every single occurrence checked, never body text. A second candidate signal — letter-spacing ("Í T É L E T") — was rejected after the same check: some titles are plain, unspaced caps ("INDOKOLÁS", "ÍTÉLETET:"), so it would have missed real titles rather than just risking false positives.

Since these titles are flat (no "H1 > H2" nesting the way Markdown headings can nest), `DocxExtractor` reuses `MarkdownExtractor`'s section-index/header-breadcrumb *output shape* (`ChunkMetadata.header_path`, `page_number`-as-section-index) but with a much simpler builder — just "which centered title came most recently before this word," no header stack to maintain.

## 2026-09-29 — Chunk packaging: rejected `ProcessedChunk`/`ChunkPacker`, extracted a smaller fix (`64a3c75`)

Károly asked for a `ProcessedChunk` type (distinct from `Chunk`) and a `ChunkPacker`/`ChunkEnricher` component to own header-breadcrumb prefixing *and* token-budget enforcement, motivated by a real observation: `SplitOverflowStrategy.apply()` was reverse-engineering `chunk_document()`'s header-embedding format — stripping `enrich_chunk_content()`'s output back off via a string-prefix check — to re-split an already-packaged chunk without duplicating or double-counting its header. That coupling is real and worth fixing.

The two-part proposal was scoped down before implementing, for reasons that mirror the 2026-09-29 Clean Architecture entry below:
- **No `ProcessedChunk` type.** `Chunk` already *is* the packaged, embedding-ready shape — in `chunk_document()`, `Chunk.content` is already header-enriched. A second type with no new fields would just be `Chunk` under another name, working against the same day's minimal-model-set decision (see the Clean Architecture entry below, which introduced `models.py`).
- **No `ChunkPacker` owning token-budget enforcement.** That's already `ChunkOverflowStrategy`'s explicit, `.env`-selected job (`WarnOverflowStrategy` vs. `SplitOverflowStrategy`). Giving a second component that same authority would blur `WarnOverflowStrategy`'s whole point (warn, don't correct) and create two places that could disagree about whether a chunk fits.

What actually landed instead: `_strip_header_prefix()` in `ingestion/chunker.py`, written as `enrich_chunk_content()`'s explicit inverse and kept immediately next to it, plus `_package_chunk(content, metadata) -> Chunk` as the single place both `chunk_document()` and `SplitOverflowStrategy.apply()` go through to build a chunk — removing the implicit, unenforced format contract without adding a new type or a competing authority over the token budget.

## 2026-09-29 — Clean Architecture re-discussion: targeted fixes instead of a layered rewrite (`c91b35c`)

Károly proposed migrating to Clean Architecture (Entities/Use Cases/Interface Adapters/Frameworks, with a strict Dependency Rule) ahead of scaling up to the 10,000+ document legal corpus, explicitly as both a real concern and a hands-on learning goal. `AGENTS.md` already had a dated, considered rejection of DDD/layered ceremony for this project (2026-09-17) — the honest way to answer "should we revisit that" was to actually check the current code against the three concrete complaints (SOLID/SRP, OCP, DIP) rather than debate architecture styles in the abstract.

**What the code review actually found:**
- **SRP**: `agent.py`, `query/retrieval.py`, and `store.py` were already thin/focused — `store.py` in particular already *is* what the proposal called an "Interface Adapter/Repository," just not filed under that name. The one real hotspot: `ingestion/ingest.py`'s `add_document()` mixed real dedup/versioning business logic (skip-unchanged / alias-duplicate / replace-previous-version / insert-new, ~30 lines of branching) directly into what's supposed to be a thin orchestrator, and `add_directory()` had a near-duplicate of the same branching.
- **OCP**: already well served — the Strategy/Driver pattern runs across embedding, LLM, reranker, *and* retrieval strategy (4 independent hierarchies), plus the deliberately-different extractor dispatch. Nothing to extend here; the proposal's "can we extend this to extractors/vector-DBs too" question turned out to already be "yes, extractors already do."
- **DIP**: `ingest.py`/`retrieval.py` depend on a concrete `VectorStore` class, not an ABC. But there is exactly one backend (Postgres+pgvector) and no concrete plan for a second — a `VectorStoreRepository` ABC with one implementation would be the textbook premature abstraction this project's own top-level guidance warns against.

**The agreed compromise** (all three items delivered in commit `c91b35c`):
1. Extracted the dedup/versioning decision into a pure, unit-tested `_resolve_ingest_action()` (`ingestion/ingest.py`) — fixes the one real SRP hotspot, and as a bonus removes the near-duplicated branching between `add_document`/`add_directory`. See `AGENTS.md`'s "Orchestrator functions must stay thin" bullet.
2. Introduced typed `dataclass`es (`models.py`: `ChunkMetadata`, `Chunk`, `RetrievedChunk`) in place of the untyped chunk dict, motivated by the corpus's upcoming richer metadata (header paths, section breadcrumbs) making typo'd dict keys a real risk. Not a full Entity layer — no validation logic, no framework independence beyond what a plain dataclass already gives; Postgres JSONB storage unchanged (`to_dict()`/`from_dict()` are the only serialization boundary).
3. Deliberately did **not** introduce a `VectorStoreRepository` ABC — no second backend to justify it (see DIP finding above).

Explicitly NOT done, and why: no Entities/Use-Case/Interface-Adapter folder restructuring, no dependency-injection framework, no bounded contexts. The project's domain is still a linear pipeline with no complex business invariants to protect — the two real problems named above had small, targeted fixes, and manufacturing a bigger architectural exercise around them would have been solving a problem the codebase didn't actually have.

## 2026-09-29 — Corpus acquisition: reverse-engineered eakta.birosag.hu's search/download endpoints (`b157435`)

Built `corpus/download_court_decisions.py` to collect a large (10,000+ document), realistic real-estate-law corpus for the upcoming large-scale retrieval/answer-accuracy eval (profiled user questions, a golden set — see the RAG-accuracy-at-scale direction). No public API exists for the site's "Bírósági Határozatok Gyűjteménye" (anonymized court decisions), so the actual request shape was reverse-engineered from the page's embedded JavaScript (the "ENCO.Grid" component) and verified against live responses rather than assumed.

**Findings that shaped the script:**
- The search (`POST /AnonimizaltHatarozat/Search?Area=`) is a plain JSON API — no headless browser or HTML scraping needed, simpler than expected. Getting the request shape right took actual trial and error: the site's own JS builds `KeresoSzavak[]`/`KeresoSzoOperatorok[]` array params, and a wrong operator enum value (guessed as `"AND"`/`"OR"` before finding the real `KeresoSzoOperatorDropdown` options: `Osszes`/`Kifejezes`/`Pontos`) produces a generic, misleading "Hiba történt..." error with no indication of which field is wrong.
- The `HatarozatFajta` filter (Ítélet/Végzés) accepts exactly one value per search — getting both types requires two separate searches, deduplicated by `(court, case_number)` across all of them.
- **The "native format" download endpoint doesn't always return RTF** — it returns whichever format the source court originally filed in, RTF *or* DOCX, with the real format only knowable from the response's `Content-Type`/`Content-Disposition` headers, not assumable from the request. The script reads this back per-download rather than hardcoding an extension.
- Inspecting a real DOCX/RTF pair showed neither uses Word "Heading" styles for section titles (e.g. "ÍTÉLET", "INDOKOLÁS") — the actual convention is a **centered, letter-spaced paragraph** (`w:jc="center"` in DOCX, `\qc` in RTF), confirmed identically in both formats for the same section marker. This is a cheap, reliable, markup-level signal — unlike PDF, which would need coordinate/font-size heuristics for the same job — and is the planned basis for a future header-enrichment pass on this corpus, analogous to the Markdown extractor's `header_path` (see the 2026-09-27 entry above), once ingestion-side RTF/DOCX extractors exist.

**Resume-safety, added after being asked directly "what happens if this gets interrupted":**
- File writes are atomic (write to a `.part` temp file, then rename) — a crash/power-loss mid-write can never leave a truncated file that a later run would mistake for a complete download.
- `meta.csv` is append-only and a re-run only treats a `(court, case_number)` as done if its *latest* recorded status is `downloaded`/`already_downloaded` — a row left at `error` (e.g. from a transient network outage) is automatically retried on the next run instead of being skipped forever.

## 2026-09-19 — MCP server: five real bugs found integrating with a real host (`fb5af0a`)

Found by testing `mcp_server.py` against a real MCP client (Claude Desktop), not by inspection or reading the SDK's docs alone:

1. `ingestion/ingest.py`/`query/retrieval.py` used to report progress via `print()`. Over MCP's stdio transport, stdout is reserved for the JSON-RPC protocol — a stray `print()` line landed on that channel mid-call and broke a real client's message parsing (`Failed to parse JSONRPC message from server`), confirmed by spawning `mcp_server.py` as a real subprocess and calling both tools over the actual protocol. Fixed by switching both modules to Python's `logging` module (stderr by default, invisible to the protocol stream) — `agent.py`/`scripts/eval_cli.py`/the `make add-document`/`query` targets configure a bare `logging.basicConfig(format="%(message)s")` so their own CLI output looks exactly as before.
2. `uv run mcp install`'s own generated launch command (`uv run --with "mcp[cli]==X.Y.Z" mcp run <path>`) is built for a standalone, dependency-free single-file script — the SDK's own docs say so explicitly. `mcp_server.py` isn't that: it imports the whole project (`psycopg2`, `openai`, `sentence-transformers`, ...). Registering it as-is and launching from Claude Desktop failed immediately with **"Server disconnected"**; reproduced directly by spawning the exact generated command from an unrelated directory with a clean environment (no inherited venv, matching how Claude Desktop actually spawns it): `ModuleNotFoundError: No module named 'psycopg2'`. Fixed with `uv run --project <docs-agent dir> mcp_server.py` instead, which resolves against this project's own environment regardless of the caller's working directory. `make mcp-install` automates this registration and rewrites the generated config entry with the `--project` flag and required environment variables automatically.
3. **`add_document()` had no protection against re-ingesting the same file** — asking Claude Desktop to add a document already in the knowledge base silently duplicated its chunks. With a small corpus and a fixed `RETRIEVAL_TOP_K`, duplicate copies of the same chunks crowded out other, genuinely relevant unique chunks from a real query's top-k results — directly degrading answer quality, not just cleanliness. `add_document()` now raises `ValueError` if `VectorStore.has_chunks_from_source()` says the file's already present, with an explicit `force=True` escape hatch for genuinely wanting a duplicate.
4. When forced to answer from the knowledge base alone (via `/my-docs`), the model correctly identified that a "Technology Stack" list was retrieved incompletely — a bullet point split across two adjacent chunks, and the query only surfaced one of them. Root cause, confirmed by inspecting `retrieve_chunks()`'s actual output: it was bug 3 above — duplicate chunks were occupying the other top-k slots that should have gone to the chunk with the rest of the list.
5. Re-adding an already-present document (bug 3's guard, working as designed) surfaced with a **completely blank error message** in Claude Desktop. Cause: `mcp_server.py`'s `add_document` let the plain `ValueError` propagate, and the MCP SDK treats any exception besides its own `ToolError`/`MCPError` as an unexpected crash — deliberately hiding the exception's text from the client. Fixed by catching `ValueError`/`FileNotFoundError` (the specific, "the model could retry with different arguments" cases) and re-raising as `ToolError`, whose message does reach the client.

## 2026-09-18 — Hybrid search: full-text query was silently ANDing every word of the question (`b6b3d34`)

Found while building the retrieval eval script, not by inspection: `search_fulltext()` originally passed the raw question straight into `websearch_to_tsquery('simple', question)`. The `simple` text-search configuration has no stopword list (chosen deliberately, since the corpus mixes Hungarian and English), so every word of the question — including grammar words — became a **mandatory** term (`websearch_to_tsquery` ANDs bare words together). A real chunk almost never contains a question's grammar words verbatim, so keyword search was silently returning **zero results for nearly every natural-language question**, undetected until the eval script's real numbers showed `0 keyword result(s)` on every single run.

Fixed by OR-joining the question's words (`" or ".join(query_text.split())`) before passing them to `websearch_to_tsquery`, so a chunk matching *any* of the question's content words now contributes to RRF fusion. Covered by a unit test (asserts the OR-joined string reaches the query) and a DB test (a real sentence full of grammar words that would have failed pre-fix).

## 2026-09-18 — Chunking: paragraphs spanning a page boundary were silently truncated (`fabbabe`)

Chunking used to run per page (`chunk_pages()`), with no overlap between pages — a paragraph that happened to span a page break was silently split into two truncated, unrelated chunks. `ingest.py` now concatenates the whole document first (`pdf_loader.extract_document_text()`) and chunks that (`chunker.chunk_document()`), so there's no page loop left to truncate anything at a page boundary. `chunk_pages()` itself is unchanged and still used by `eval_cli.py extract`-adjacent tooling and its own tests.

Since a chunk's words can now come from more than one page, `page_number` in its metadata is assigned by majority vote (whichever page contributed the most words) rather than a page range.

## 2026-09-17 — Chunking: `split` shown to catch what `warn` misses (`2404c3e`)

Verified against a real document, with an earlier embedding model whose sequence limit was 128 tokens (not the current default model's 512): with `CHUNK_SIZE=50` words and `WORDS_PER_TOKEN=0.4`, the `warn` heuristic estimated `50 / 0.4 = 125` tokens — just under the 128-token limit, so it **didn't warn at all**. Yet 8 of the 21 actual chunks (38%) really did exceed 128 tokens (up to 198), because real token count varies a lot per chunk's content, not just per configured size. `split` caught and corrected all 8 (21 → 29 chunks), each landing between 53 and 127 tokens — no near-empty stragglers, and afterward zero chunks exceeded the limit.

This is the finding that later motivated making `split` the default (see the 2026-09-26 chunking-defaults entry above).
